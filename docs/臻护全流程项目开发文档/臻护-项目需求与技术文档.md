## 一、项目简介与背景

### 1.1 项目名称与定位

**臻护** (ZhenHu) 是一个面向医院住院病区的**全病程数智协同平台**。它在医院现有信息系统 (HIS) 之上架设一层 AI 增强的临床协同与决策辅助层 —— 不是 HIS 的替代品或竞争品，而是让 HIS 里的数据真正流向照护团队的桥梁。

**定位一句话:** 连接 HIS 数据和临床照护团队，让入院 → 住院 → 出院 → 随访的每一环都有 AI 辅助和团队协同。

### 1.2 行业背景

#### 1.2.1 中国住院医疗现状

中国年住院人次约 **3.0 亿** (2024 年卫生健康统计公报)。三级医院平均住院日 8.1 天，但一线临床团队普遍面临严重的"信息断层" —— HIS 积累了海量数据，却不能直接服务于临床决策。

**现状数字:**

| 指标 | 数值 | 来源 |
|------|:--:|------|
| 全国医疗卫生机构 | 107 万 | 2024 统计公报 |
| 三级医院 | 3,500+ | 2024 统计公报 |
| 年住院人次 | 3.0 亿 | 2024 统计公报 |
| 执业(助理)医师 | 450 万 | 2024 统计公报 |
| 注册护士 | 560 万 | 2024 统计公报 |
| 医护比 | 1:1.25 | (目标 1:1.5+) |
| 三级医院平均住院日 | 8.1 天 | 2024 统计公报 |

**五个典型时间黑洞:**

| 场景 | 每例耗时 | 根因 | 年累计 (1 个科室) |
|------|:--:|------|:--:|
| 入院评估 | 30-45 分钟 | 医生凭记忆检索 DDx，手动计算 NEWS2/qSOFA/Padua 评分，逐条核对用药 | ~750 小时 |
| 药物核对 | 5-10 分钟 | 开新药不自动审查与患者已有药的相互作用、过敏禁忌、剂量调整 | ~300 小时 |
| 每日查房记录 | 15-20 分钟 | SOAP 笔记手工书写，体征趋势手动翻页查找 | ~600 小时 |
| 护理交接班 | 20-30 分钟/班 | 口头+手写交班，信息遗漏率 30%，关键体征遗漏是医疗差错的首要原因 | ~500 小时 |
| 出院准备 | 20-30 分钟 | 出院小结是"病历摘抄"不是"照护计划"，患教靠口头说 | ~400 小时 |

**更深层的问题:**

```
三级医院住院病区的真实日常:

07:30  护士交班 ── 口头念名字+病情，"3 床心率偏快，注意一下"
08:00  医生查房 ── 在 HIS 里翻患者 3 天前的化验单，"上次肌酐多少来着?"
09:30  开新药   ── 心内科患者 + 糖尿病 + CKD 3 期，新开 ACEI 会不会跟现在的
                  螺内酯冲突? 手动查药物手册 → 5 分钟
11:00  接到检验危急值电话 ── "32 床血钾 6.2!" → 停 ACEI + 补钙 + 通知医生
14:00  下午查房 ── "上午的血气分析出来了吗?" → HIS 里找了 3 分钟
16:00  出院谈话 ── "回家药怎么吃? 什么情况要马上来医院?"
                  口头讲一遍 → 患者家属点头 → 3 天后因心衰加重再次入院
17:30  晚交班   ── "白班收了 3 个，出院 2 个，32 床血钾高处理了"
                  → 夜班护士: "32 床为什么血钾高? 之前血钾多少?"
```

这不是某个医院的问题，是全国 3,500+ 家三级医院的普遍现状。HIS 为收费和合规设计，LIS/PACS 为检验和影像设计，但它们之间存在巨大的 **"照护间隙"** —— 没有系统负责把数据转化为可执行的临床决策。

| "十四五"全民健康信息化规划 | 2022 | 互联互通、区域协同、全生命周期健康管理 | FHIR 适配器 + 出院随访延续 |

**行业趋势:** 2025-2026 年三大变化加速了"在 HIS 之外做临床 AI"的可行性:

```
① HIS 厂商开放 API      → FHIR 标准接口逐渐普及, 不再排斥第三方对接
② LLM 临床推理成熟     → DeepSeek V4-Pro 等国产模型达到可用水平
③ 医院信息化预算增长    → 三级医院年信息化投入超千万, CDSS 被明确要求
```

**竞争格局:**

| 类型 | 代表 | 差异 |
|------|------|------|
| 传统 CDSS (知识库查询) | 惠每、森亿、卫宁 | 规则库驱动, 不做 Agent 自动推理 |
| AI 辅助诊断 (影像/病理) | 推想、数坤、科亚 | 单点 AI, 不做全流程临床协同 |
| 护理信息系统 | 医惠、联达 | 任务执行系统, 不做 AI 辅助决策 |
| 出院管理系统 | 部分 HIS 厂商 | 流程模块, 不做延续护理 + 随访 |
| 大模型通用助手 | ChatGPT/文心/通义千问 | 通用对话, 不接入病历, 无临床角色系统 |
| **臻护** | — | **全流程 Agent 管线 + 角色协同 + 证据追溯 + 延续护理** | |

#### 1.2.3 系统边界

**臻护做什么:**
- AI 辅助入院评估 (DDx 鉴别诊断 + 自动评分)
- 医生待办审核队列 + 护士任务队列
- 药物交互实时预警 + 过敏禁忌检查
- 临床证据追溯 (RAG 16 层知识库)
- 出院标准判断 + 患教生成 + 照护计划
- 随访联系人与任务管理
- 知识图谱临床推理 (Neo4j 证据链)

**臻护不做什么:**
- 不替代 HIS 写病历 / 开医嘱
- 不替代 LIS 出检验报告
- 不替代 PACS 存储影像
- 不替代 OA/钉钉 审批流程

## 二、痛点分析

### 2.1 核心矛盾：数据在 HIS 里，决策靠人脑

```
┌─────────────────────────────────────────────────────────┐
│                    信息断层的代价                         │
│                                                         │
│  HIS 有数据                 ╳          临床照护团队       │
│  ┌──────────────────┐     (桥在哪?)   ┌──────────────┐  │
│  │ 入院记录 · 病程    │                │ 科主任        │  │
│  │ 医嘱 · 检验报告    │     ╱ ╲       │ 住院医师       │  │
│  │ 护理记录 · 体温单  │    ╱   ╲      │ 护士长        │  │
│  │ 知情同意 · 会诊    │   ╱ 照护 ╲     │ 主管护师       │  │
│  │ 出院小结 · 费用    │  ╱  间隙  ╲    │ 药师          │  │
│  └──────────────────┘ ╱           ╲   └──────────────┘  │
│                      数据 ≠ 决策                          │
│                                                         │
│  结果: 关键信息在 HIS 里沉睡，临床决策靠经验和记忆         │
└─────────────────────────────────────────────────────────┘
```

HIS 为**结算和合规**设计，不是为**临床决策**设计。这决定了它的数据组织方式天然不适合医生查房、护士交班、药师审方的思维流程。

### 2.2 七大临床痛点深度剖析

---

#### 痛点 1：入院评估 —— "一人一电脑，凭记忆看病"

**现状:**
```
心内科新收一名胸闷气促的患者。
接诊医生需要:
  ① 回忆: "鉴别诊断考虑什么? 心衰? ACS? 肺栓塞? 主动脉夹层?"
  ② 计算: NEWS2 评分需要 6 个参数 → 手动查表 → 2 分钟
  ③ 核对: 患者在家吃的 7 种药之间有没有相互作用? → 翻药物手册 → 5 分钟
  ④ 评分: Padua VTE 风险评估 (11 项)、Morse 跌倒评分 (6 项)、Braden 压疮评分 (6 项)
  ⑤ 决策: 综合以上 → 制订初步诊疗计划

整个过程 30-45 分钟, 全靠医生的知识储备和记忆。
凌晨 2 点急诊入院时, 值班医生精力不足, 遗漏风险最高。
```

**量化后果:**
- DDx 遗漏: 研究显示急诊科 DDx 初诊遗漏率 10-15%
- VTE 漏评: 住院患者 VTE 风险评估率仅 50-60% (未评估的患者中 VTE 发生率 3-5 倍)
- 药物交互: 老年人平均用药 6-8 种, 严重交互发生率 15-20%

**臻护方案:**
```
HIS 通知入院 → Agent 自动读取病历 → 并行运行:
  ├─ node_ddx: 生成 DDx 列表 (含证据来源 + 可能性排序)
  ├─ node_medication_reconciliation: 交叉比对 7 种药的交互矩阵
  ├─ node_news2 / node_qsofa / node_padua_score: 自动评分
  └─ node_batch_scoring: 4 项评分并发 → 8 秒出结果

→ 医生打开工作台 → 待审队列显示该患者 → 核查 AI 结果 → 确认/修改
→ 全程 5-8 分钟, AI 预填 80%, 医生审校 20%
```

---

#### 痛点 2：待办审核 —— "DDx 在哪里? 出院签字在哪里? 不在一页上"

**现状:**
```
医生一天的工作:
  □ 5 床 DDx 待确认 → 点开 HIS "诊疗记录" → 找到入院页 → 翻到 DDx 栏
  □ 8 床用药核对 → HIS "医嘱管理" → 长期医嘱 → 临时医嘱 → 逐条核对
  □ 12 床出院签字 → HIS "出院管理" → 出院小结 → 交接清单
  □ 15 床会诊请求 → HIS "会诊系统" → 会诊申请 → 会诊意见

每个任务在不同菜单中, 没有统一的"待办视图"。
医生需要在 HIS 的 6-8 个菜单之间反复切换, 认知负荷极高。
```

**量化后果:**
- 每天切换菜单 50+ 次
- 每例待办平均需要打开 2-3 个页面
- 每周因"没看到待办"延误审核 2-3 次

**臻护方案:**
```
医生工作台 → 统一的 4 标签待审队列:
  [DDx 2] [用药 0] [出院 1] [告警 N]
       │
       点击患者行 → DiffPanel 右侧滑出
        ├─ 审核模式 (DDx/用药/出院)
        ├─ 证据来源 (EvidencePanel ← RAG 引用)
        └─ 确认/驳回/重新生成 → 提交 (含 expected_version)
```

---

#### 痛点 3：药物交互 —— "新开一种药，可能踩四颗雷"

**现状:**
```
患者: 心力衰竭 + 房颤 + 糖尿病 + CKD 3 期
当前用药: 华法林 2.5mg qd + 地高辛 0.125mg qd + 螺内酯 20mg qd
         + 赖诺普利 10mg qd + 二甲双胍 500mg bid

新开: 克拉霉素 500mg bid (呼吸道感染)

实际风险:
  ❌ 克拉霉素 (CYP3A4 抑制剂) + 华法林 → INR 可能飙升 2-3 倍 → 大出血
  ❌ 克拉霉素 + 地高辛 → 地高辛浓度可能翻倍 → 心律失常
  ❌ 赖诺普利 + 螺内酯 → 已经在用, K⁺ 监测中
  ❌ 二甲双胍 + CKD 3 期 → eGFR 30-44, 需减量 (最大 1000mg/d)

没有系统自动提示这些交互,
全靠医生在繁忙中自己查 —— 现实是, 很多时候没时间查。
```

**量化后果:**
- 药物不良事件 (ADE) 占住院不良事件的 15-20%
- 其中 50-70% 是可预防的
- 严重交互漏检: 抗凝 + 抗血小板联用, 出血风险被低估 40%
- 老年患者多重用药 (≥5 种) 占 65%, 其中 40% 存在至少 1 种不合理联合

**臻护方案:**
```
Agent node_medication_reconciliation:
  ├─ 规则引擎: 交叉比对 25 组已知严重交互
  ├─ LLM: 补充罕见交互 (数据库 + RAG)
  └─ 输出: 交互矩阵 + 严重程度标签 + 建议方案

Dashboard MedicationSafetyPanel:
  ├─ 红色标签: 禁忌
  ├─ 橙色标签: 严重
  ├─ 黄色标签: 中等
  └─ 每对交互的药物名 + 机制 + 建议

护士评估 (node_nursing):
  ├─ 识别高风险患者 (抗凝 + 跌倒风险 → 预防措施)
  └─ 异常体征触发 AI 护理建议
```

---

#### 痛点 4：护理信息孤岛 —— "交接班靠嘴说，关键信息说漏了"

**现状:**
```
白班护士交班:
  "15 床心衰, 出入量负的 800, 血压还行。
   8 床 感觉有点喘, SpO2 93%, 你注意一下。
   3 床明天出院, 交代一下药怎么吃。"

夜班护士 2 小时后:
  "15 床出入量昨天白天多少? 我看看... (翻护理记录本)
   8 床怎么喘了? 是今天才开始的还是一直这样?
   3 床出院交代什么? 有模板吗?"

口头交班的固有缺陷:
  - 选择性遗忘: 只记得自己觉得"重要"的, 可能和接班人的关注点不同
  - 无结构化: 没有 S-B-A-R 框架, 信息碎片化
  - 不可追溯: 说过了但没记录 = 等于没说
```

**量化后果:**
- SBAR 交班可将信息遗漏从 30% 降至 10%
- 80% 的严重医疗差错涉及交接班沟通失败
- 护士每个班次平均负责 8-12 名患者 (三级医院), 信息过载是常态
- The Joint Commission 将"交接班沟通"列为患者安全目标

**臻护方案:**
```
护士看板 → 打开即可看到:
  ├─ AI 优先级建议 (NEWS2≥5 排最前)
  ├─ 体征待测列表 (逾期自动告警)
  ├─ 任务队列 (按类型: 生命体征/护理措施/用药核对/制度核查)
  └─ SBAR 交班报告:
       ├─ 重点关注 (high_focus)
       ├─ 病情稳定 (stable)
       └─ 今日出院 (discharge_today)
           └─ 可选 AI 交班要点 (LLM 增强)
```

#### 痛点 5：出院交接断裂 —— "小结是摘抄，不是照护计划"

**现状:**
```
出院当天的典型场景:

医生: "回家药按时吃，不舒服随时来。"
      → 花 3 分钟口述 → 患者点头 → 签字出院

出院小结:
  "患者因心力衰竭入院... 经强心利尿扩血管治疗后病情好转...
   出院带药: 呋塞米 20mg bid, 螺内酯 20mg qd..."

问题:
  ❌ 小结是病历摘抄, 不是"照护计划"
  ❌ "呋塞米 20mg bid" —— 但患者家属不识字, 能把药认对吗?
  ❌ "不舒服随时来" —— 什么情况算需要来? 喘? 肿? 体重涨了多少?
  ❌ 出院后谁来跟? 药吃完了去哪续? 复诊挂谁的号?

3 天后:
  患者因心衰加重再次入院。
  原因: 回家后觉得自己"好了", 停了利尿剂, 喝了太多水。
```

**量化后果:**
- 心衰患者出院 30 天再入院率: 20-25% (中国)
- 其中 50-60% 被认为可通过更好的出院管理预防
- 药物依从性: 出院 1 个月后仅 60% 患者正确服药
- Teach-back 法可将再入院率降低 45%

**臻护方案:**
```
医生发起出院 → Agent node_discharge:
  ├─ 出院标准自动判断 (病种模板核对)
  ├─ Bridge 创建臻护病例 + 照护视图
  ├─ AI 患教内容生成 (DischargeEducationPanel):
  │    ├─ 药品清单 (药名 + 图片 + 剂量 + 频次 + 注意事项)
  │    ├─ 饮食限制 (咸/水/糖)
  │    ├─ 急症识别 (什么情况立即来医院)
  │    └─ Teach-back 验证 (让患者复述)
  └─ 随访任务创建:
       ├─ 7 天电话随访
       ├─ 30 天复诊提醒
       └─ 随访联系人 (加密联系方式)
```

#### 痛点 6：知识沉淀为零 —— "师傅带徒弟，经验带不走"

**现状:**
```
心内科李主任从医 25 年, 对难治性心衰的处理有独特经验。
但他退休后, 这些经验就带走了。

年轻医生遇到复杂病例:
  "上次跟李主任看过一个类似的..."
  → 翻找旧病历 → 30 分钟 → 没找到

医院每例出院都有宝贵的临床数据,
但无法结构化存储、检索、复用。
```

**臻护方案:**
```
RAG 16 层知识库 (385 条) + Neo4j 证据图谱:

  ┌─ 权威指南 (L1-L16: 评分/药物/检验/急症/护理/营养/妇产/中医)
  ├─ 病种模板 (22 个: 出院标准 + 并发症 + SOAP 模板)
  ├─ 证据图谱 (Neo4j: 疾病→症状→检查→药物→指南 路径可视化)
  └─ 科室清单 (16 科室 67 项差异化核查)

  → 医生查房时: "这个心电图变化提示什么?"
    助手 RAG 检索 → 带引用回答

  → 出院时: "这个病种出院标准是什么?"
    模板自动匹配 → 逐条核对

  → 管理端: "我们科室 VTE 预防率是多少?"
    KPI 看板 → 知识库热力图 → 薄弱环节一目了然
```

---

#### 痛点 7：数据碎片化 —— "一个患者的资料散落在四个地方"

**现状:**
```
医生想要了解一个住院患者的全貌, 需要:
  □ HIS: 病历 (入院记录 + 病程)
  □ LIS: 检验报告
  □ PACS: 影像
  □ 护理系统: 体温单 + 护理记录
  □ 心电系统: ECG
  □ 药房系统: 用药记录

没有一个地方能看到 "这个患者现在怎么样" 的完整回答。
```

**臻护方案:**
```
患者 Dashboard — 一个页面, 9 个面板:

[HeaderRow]  病种 badge · NEWS2 色标 · 入院天数 · 出院准备度
[PanelA]     入院采集 (主诉 + 病史 + PE)
[PanelB]     评分面板 (NEWS2 / qSOFA / Padua / Morse / Braden)
[PanelC]     用药安全 (交互矩阵 + 过敏禁忌 + 缺口/重复)
[PanelD]     体征趋势折线图 (SpO2 / HR / BP 时序)
[PanelE]     检验趋势 (异常值红色标记 + 参考范围)
[PanelF]     SOAP 查房记录 (S-O-A-P 四列)
[PanelG]     照护管理 (开药 / MDT / 教育 / 随访)
[PanelH]     证据图谱 (Neo4j 路径可视化)
[PanelI]     临床告警 (红色 critical / 橙色 warning / 灰色 info)
```

### 5.2 单服务架构决策

臻护选择**单体 FastAPI 应用**而非微服务拆分:

| 决策 | 理由 |
|------|------|
| 单体非微服务 | 当前临床接口共享同一事务边界；过早拆分会引入分布式事务复杂性 |
| 内部模块分层而非拆服务 | routes → services → agent, 清晰分层但共享进程 |
| 同一数据库 | SQLite/MySQL 单实例, State Store 共库 |
| 外部依赖独立 | Milvus / Neo4j / Redis 各自独立部署, 降级不阻塞 |

### 5.3 内部模块边界

```
routes/     ── HTTP 层, 只做参数解析 + 调用 service + 返回
services/   ── 业务层, 事务管理 + 权限控制 + 数据聚合
agent/      ── AI 层, LLM 调用 + RAG 检索 + DAG 编排
domain/     ── 领域模型 (当前仅占位)
hooks/      ── 外部系统桥接 (FHIR, Bridge)
middleware/ ── 横切关注点 (认证, 幂等, 日志)
```

### 7.7 通用规范

- **认证:** 所有受保护端点需 `x-role` + `x-title` + `x-department` headers (dev) 或 `Authorization: Bearer` (jwt/oidc)
- **响应格式:** `{ "request_id": "...", "data": {...} }` (成功) 或 `{ "request_id": "...", "error": { "code": "...", "message": "..." } }` (失败)
- **版本控制:** 写操作携带 `expected_version` → `409 STATE_VERSION_CONFLICT`
- **幂等性:** 写操作支持 `Idempotency-Key` header 防重复

## 八、Agent 智能管线

### 8.1 架构

当前为 `GRAPH_MODE=classic` 的有向图 (DAG)，包含 27 个核心节点和 Human-in-the-loop。待审核状态由状态库与审核接口保存；`GRAPH_MODE=stateful` 的 LangGraph checkpoint 暂停/恢复尚未完成持久化验收，系统会拒绝该模式。

> 流程、Loop Harness、DeepAgent、人工审核与前端演示细节见 [臻护-Agent全流程、Loop Harness与DeepAgent实战手册.md](臻护-Agent全流程、Loop Harness与DeepAgent实战手册.md)。

```
入院流程:    admission → history → exam → ddx → medication_reconciliation
               → triage → doctor_confirm → batch_scoring
                 (NEWS2/qSOFA/Padua/VTE 并发) → mdt_trigger → stroke

住院流程:    doctor_confirm 之后 → daily_round → nursing
               → shift_summary → lab_review → monitoring
               → medication_adjust → transfer → doctor_review

出院流程:    discharge → handoff → doctor_discharge_sign → patient_confirm
```

- **一键重建索引:** 二次确认 → 清空 16 集合 → 重新编码 → 写入
- **校验:** 缺失/重复/过期条目检测

### 12.3 并发安全

```
写操作携带 expected_version (乐观锁)
  ├─ version 匹配 → 事务提交 → version+1
  └─ version 不匹配 → 409 STATE_VERSION_CONFLICT
       └─ 前端: 保留本地草稿, 提示刷新, 不自动重放

幂等性: Idempotency-Key header
  ├─ 首次 → 写入 + 缓存响应
  └─ 重复 → 返回缓存响应
```

## 十五、当前交付、运行与治理

本章面向当前本地联调、演示、交接和后续部署准备。它描述“代码已经具备什么”和“应如何安全使用”，不以演示能力代替临床生产验收。易变的运行数值以同目录《臻护-代码现状基线》为准。

### 15.1 三端工作区与正式入口

| 工作区 | 正式路由 | 兼容入口 | 主要身份 | 首要工作 |
|------|------|------|------|------|
| 医生工作台 | `/department/:department/doctor` | `/workbench` | 科主任、住院医师 | 待审核、病区优先级、查房、患者处置与出院 |
| 护理工作台 | `/department/:department/nurse` | `/nurse` | 护士长、主管护师 | 班次任务、逾期监测、患者护理、交班与核查 |
| 统一管理端 | `/department/:department/management` | `/admin` | 科主任、主任医师、护士长 | 科室运行、知识治理、证据图谱、模板、组织与运维 |

科主任与护士长进入同一个管理端，不存在独立的旧“护士 admin”产品面。管理端按身份提供不同重点：医生管理者侧重病区、模板与集成，护士管理者侧重护理质量、交班、清单与知识治理。

患者详情是医生端工作流的一部分，兼容路由为 `/patient/:id`，出院工作区为 `/patient/:id/discharge`。护理端从患者目录/任务进入护理详情，不将医生处置能力复制为护理权限。

### 15.2 双科室演示病例包与重置边界

当前代码提供 `2026-07-21.1` 演示病例包：`心内科`、`呼吸科`各 10 名，共 20 名虚构患者，贯穿在院监测、查房/审核、护理任务、出院交接和出院后随访。其目的是为三端界面提供内部一致、可重复的联调数据，而不是临床真实数据或匿名化病历。

管理端的 `SystemOperationsPanel` 通过 `GET /inpatient/admin-capabilities` 判断 `demo_patient_reset`，可发起 `POST /inpatient/fixtures/reset-demo`。请求必须带 `{ "confirmed": true, "purge_runtime": true }`：运行时患者状态会被清理并重建 20 例；知识库、组织、模板与审计日志不受影响。该能力只允许开发/演示环境管理者使用，生产环境硬性禁用，并写入管理审计事件。联系人数据按 `CONTACT_ENCRYPTION_KEY` 加密，页面只获得掩码联系方式。

护理任务视图按工作流只展示仍需护理执行的在院患者，因此不要求与全部 20 例病例数相等；已进入交接或随访的病例应从出院与随访面板验证。

### 15.4 当前 API 使用原则

当前本地 `8001/openapi.json` 为 `164` 个路径、`166` 个操作，其中包含 `/v1/*` 兼容别名。前端以主路径调用，不能把兼容别名当作重复功能开发。

| 域 | 推荐主接口 | 使用说明 |
|------|------|------|
| 管理能力 | `GET /inpatient/admin-capabilities` | 前端根据 `is_manager`、`writes_enabled`、`authorization_reason` 和 `operations` 呈现可用性 |
| 演示病例重置 | `POST /inpatient/fixtures/reset-demo` | 仅开发/演示管理者；显式确认、可选择清空运行态、生产环境固定禁用 |
| RAG 条目 | `GET /admin/rag/entries?search=&layer=&page=&page_size=` | 可解释的多字段关键词检索；`search` 支持带引号的词组 |
| RAG 语义预览 | `GET /admin/rag/preview?query=&layers=&top_k=` | `query` 必填，`layers` 可逗号分隔；不要和 entries 参数混用 |
| RAG 运维 | `GET /admin/rag/dashboard`、`/diagnostics`、`POST /admin/rag/reindex` | dashboard 看状态，diagnostics 排障，reindex 是管理者写操作 |

旧 `/inpatient/rag/index`、`/search`、`/browse`、`/validate` 仅作兼容或直接诊断接口。管理端日常操作使用 `/admin/rag/*`。

### 15.5 Agent、LLM 与临床安全边界

当前运行模式为 `GRAPH_MODE=classic`。`GRAPH_MODE=stateful` 尚未具备持久 checkpoint、interrupt/resume 和临床恢复验收，系统会明确拒绝启动，不能在演示或部署中开启。

| AI 能力 | 可见位置 | 系统行为 | 不可越过的边界 |
|------|------|------|------|
| DDx、风险解释、用药建议 | 医生工作台、患者助手 | LLM + 规则基线 + 证据引用 | LLM 不得改变既定的临床安全排序或直接签发医嘱 |
| AI 查房摘要 | 查房专区 | 汇总体征、检验、用药和病程后生成草稿 | 医生编辑、核对前不进入临床处置 |
| 护理优先级/交班摘要 | 护理工作台 | 规则优先，LLM 仅补充解释/摘要 | 不替代护士的任务完成和异常上报 |
| 建议转操作草稿 | 患者助手/草稿面板 | 生成待确认医嘱、检查或随访建议 | 批准、驳回、版本冲突和审计不可绕过 |
| 出院叙事与患教 | 出院工作区 | 模板/知识检索/LLM 个性化补充 | 出院仍由医生指令、审核、签字、交接闭环控制 |

LLM、Milvus、Redis 或 Neo4j 短暂不可用时，页面应显示明确的可重试/降级状态；规则结果、人工录入、版本控制与审计链不能依赖一次模型调用成功。

### 15.6 RAG、图谱与缓存运维

当前知识库基线为 `16` 层、`385` 条结构化知识，Milvus 索引可用。Redis 加速助手会话、查询和嵌入结果；首次语义查询可能触发嵌入模型冷启动，应查看加载/超时状态，而不是立刻判定索引缺失。

| 操作 | 先决条件 | 执行与检查 |
|------|------|------|
| 查看知识健康 | 管理身份 | `GET /admin/rag/dashboard`，确认 `total_documents`、层级 `actual/expected`、`needs_attention` |
| 排查索引问题 | 管理身份 | `GET /admin/rag/diagnostics`，记录失败层、运行时状态和维护日志 |
| 重建索引 | 管理写权限 | `POST /admin/rag/reindex`；等待编码与集合重建完成，再查询 dashboard/entries/preview |
| 检查图谱 | 管理身份 | `GET /admin/evidence-graph/status`，再查看病种与 visualization 返回的节点/关系 |
| 重建图谱 | 管理写权限 | `POST /admin/evidence-graph/rebuild`，完成后重新读取 status 和可视化接口 |

生产环境的上述写操作除管理角色外，还要求 `MANAGEMENT_OPERATIONS_ENABLED=true`，以及 OIDC/JWT claims 含 `zhenhu:admin:write` 或 `zhenhu:admin:*`。

| 日志与密钥 | 支持结构化日志，配置通过环境变量提供 | 禁止真实手机号、token、LLM key 进入日志、文档或版本库 |

## 十八、未来展望

### 18.1 愿景

> **让每一个住院患者都有一支 AI 增强的照护团队, 让每一次临床交接都安全、连续、可追溯。**

臻护的终极目标不是"替代医生", 而是 **消除照护间隙**:

```
当前:   HIS ──╲──────╱── 医生
               ╲    ╱
              照护间隙
               ╱    ╲
         LIS ──╱──────╲── 护士

未来:   HIS ── 臻护 ── 医生 (AI 增强)
        LIS ── 臻护 ── 护士 (任务协同)
       PACS ── 臻护 ── 药师 (知识驱动)
        患者 ── 臻护 ── 家属 (延续护理)
```

### 18.3 核心竞争力

| 壁垒 | 说明 | 复现难度 |
|------|------|:--:|
| **27 节点 Agent 管线** | LangGraph DAG + Human-in-the-loop + 5 模式助手 + 3 认证 | 高 (6 个月+研发) |
| **385 条 16 层 RAG 知识库** | 结构化临床知识 + 50 组同义词 + 查询缓存 | 中 (3 个月+整理) |
| **17 模型数据契约** | SQLAlchemy ORM + State Store + ClinicalFacade 事务一致性 | 中 (2 个月+设计) |
| **47 组件 React SPA** | TanStack Query + Zustand + MUI v6 + OKLCH | 中 (2 个月+前端) |
| **当前 API 表面** | FastAPI + Pydantic + 3 认证 + 幂等 + 乐观锁；OpenAPI 包含兼容别名 | 中 (持续维护) |
| **临床场景深度** | 22 病种模板 + 16 科室清单 + 医生/护士双角色全流程 | 高 (需临床专家) |

  → 全院推广: 覆盖 20+ 科室, 日均处理 500+ 患者

  → 积累中国住院患者真实世界数据

长期 (3-5 年):
  → 区域协同: 多医院数据共享, 跨院照护延续
  → AI 持续学习: 基于真实临床反馈优化 Agent 决策
  → 成为中国住院全病程管理的标准基础设施
