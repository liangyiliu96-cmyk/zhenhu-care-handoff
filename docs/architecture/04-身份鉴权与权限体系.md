# 身份鉴权与权限体系 v0.2

**状态：** 正式工程架构基线
**依据：** 需求 §2 角色权限、§7 安全审计；PoC 00-工程基线 角色矩阵；架构总览 §7 安全边界

---

## 1. 鉴权架构

```
浏览器 SPA → api-gateway (JWT 验签) → 内部服务 (X-Actor + X-Request-ID)
                 ↕
           Keycloak OIDC (自托管)
```

| 环节 | 机制 | 参考 |
|------|------|------|
| 用户登录 | Keycloak OIDC Authorization Code Flow + PKCE | 架构总览 §3.1 技术选型 |
| Token 下发 | JWT（Access: 15min / Refresh: 8h） | — |
| 网关验签 | `python-jose` 验证 RS256 签名 + `iss`/`aud`/`exp` | 参考 PoC `X-Demo-Role` 头 → JWT claim `role` |
| 角色映射 | JWT `realm_access.roles` → `ClinicalRole` 枚举 | 参考 contracts `ClinicalRole` 枚举（`doctor`/`nurse`/`case_manager`/`auditor`/`knowledge_admin`） |
| 服务间传递 | api-gateway 签发内部短 TTL JWT（5min），携带 `X-Actor` + `X-Request-ID` | 架构总览 §7 安全控制点 |

**为何不用 PoC 的 `X-Demo-Role` 头：** PoC 阶段用 HTTP Header 模拟角色以快速验证；正式工程必须由 Keycloak 签发 JWT，避免调用方伪造角色。

## 3. API 保护策略

| 层级 | 机制 | 实现位置 |
|------|------|----------|
| 端点级 RBAC | 每个路由 `Depends(assert_role_access)` | 各服务 `routes/*.py` |
| 路由中间件 | `add_request_id` + JWT 解析 | 各服务 `main.py` |
| 审计记录 | 每个非 GET 请求至少 1 条 AuditEvent | `state_machine.py` `_add_audit()` |
| 资源隔离 | `case_id` 归属校验；知识文档 `owner` 校验 | 各服务业务层 |

**PoC 对照：** PoC 的 `assertRoleAccess`（`contracts/index.mjs`）已迁移为 Python `assert_role_access`，语义一致；PoC 的服务端强制校验原则（"前端隐藏不是授权控制"）继承至正式工程。
