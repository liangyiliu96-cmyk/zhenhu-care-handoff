# 六大组件有机统一：LLM + DeepAgent + RAG + Loop + Harness + 开源API

**版本：v0.3** | **日期：2026-07-18** | **状态：方案设计**

---

## 1. 当前问题：六大孤岛

```
┌─ DeepSeek LLM ──┐    ┌─ LangGraph Agent ──┐    ┌─ Milvus RAG ──┐
│  prompt → 结果    │    │  19节点独立调用      │    │  107条知识      │
│  无路验证/无溯源   │    │  无RAG增强prompt     │    │  仅查房接入      │
└──────────────────┘    └────────────────────┘    └──────────────┘
         ↓                       ↓                        ↓
   各自独立运行，信息不互通。LLM不知道RAG有答案，Agent不知道API有数据。
   Loop 只知道跑节点，Harness 只知道算分。没有统一的数据+推理+知识管线。
```

## 2. 目标架构：统一临床智能管线

```

                          └──────┬───────────┘

                    ┌────────────┼────────────┐
                    ▼            ▼            ▼
              ┌──────────┐ ┌──────────┐ ┌──────────┐
              │  Pre     │ │  Execute │ │  Post    │
              │  Collect │ │   Agent  │ │  Refine  │
              └────┬─────┘ └────┬─────┘ └────┬─────┘
                   │            │            │
    ┌──────────────┼────────────┼────────────┼──────────────┐
    │              ▼            ▼            ▼              │
    │  ┌─────────────────────────────────────────────┐     │
    │  │            Unified Pipeline (harness.py)      │     │
    │  │                                              │     │

    │  │  ① RAG 检索        ③ LLM 推理       ⑥ 自检  │     │
    │  │  ② API 补全        ④ RAG 验证       ⑦ 溯源  │     │
```

## 3. 六组件分工（Collect→Execute→Refine 三阶段）

| 阶段 | 组件 | 输入 | 输出 | 时机 |
|------|------|------|------|------|
| **Collect** | RAG | query = 病种+当前体征+风险 | top-3 证据片段 | 每个节点前 |
| **Collect** | OpenAPI | 药物名/ICD码 | FDA标签/编码映射 | 用药核对/DDx |
| **Execute** | LLM | prompt + RAG片段 + API数据 | 结构化临床决策 | 每个节点核心 |
| **Execute** | Agent | node函数 | 状态更新 + 痕迹 | Loop编排 |
| **Refine** | RAG | LLM输出 | 验证结果(一致/矛盾/遗漏) | LLM之后 |
| **Refine** | Harness | 多源输出 | 融合打分/去重/排序 | 收尾 |

## 4. 十条优化项

### P0 — 架构级（必须做）

| # | 优化项 | 说明 |
|---|--------|------|
| **1** | **UnifiedPrompt** | 定义标准 prompt 模板：`{system}:{rag_context}:{api_data}:{patient_state}:{instruction}`，所有节点统一格式 |
| **2** | **RAG→LLM 管线** | LLM prompt 强制注入 RAG top-3 结果。`safe_llm_invoke()` 内置 RAG 预处理 |
| **3** | **LLM→RAG 验证** | LLM 输出后用 RAG 反查验证。核心字段(诊断/用药/剂量)与知识库矛盾时标记 `[需人工审核]` |
| **4** | **OpenAPI 接入 LLM Pipeline** | `clinical_external.py` 的 OpenFDA/ICD-10 结果自动 merge 到 `api_data` 字段，不用节点手动取 |
| **5** | **Collect-Execute-Refine 三阶段重构 Loop** | `loop.plan_turn()` 改为：collect(rag+api) → execute(agent) → refine(verify+merge)，替代当前平面 `for node in dag` |

### P1 — 临床精度级（应该做）

| # | 优化项 | 说明 |
|---|--------|------|
| **6** | **RAG 分层路由** | 根据节点类型自动选层：DDx→L2, 用药→L5, 护理→L8, 出院→L9, 查房→L1+L2+L6 |
| **7** | **LLM 输出结构化校验** | 每个节点 LLM 输出用 Pydantic Schema 校验。`CircuitBreaker` 触发时自动降级到规则引擎 |
| **8** | **Harness 知识增强** | `merge_comorbidity_template()` 调用 RAG 查询跨病种并发症；`compute_readiness_score()` 查 L6 检验阈值 |

### P2 — 性能体验级（可后做）

| # | 优化项 | 说明 |
|---|--------|------|
| **9** | **RAG 缓存层** | 同 query+layer 在 turn 内缓存，避免重复查询 Milvus |
| **10** | **多源溯源链** | 每个 LLM 输出附带 `source_chain: [{type:rag,layer:L2,id:dkp-xxx},{type:api,source:openfda}]`  |

## 5. 实施计划

| 批次 | 项目 | 预计影响 |
|:--:|------|------|
| **Batch 1** | P0-1/P0-2/P0-6 (UnifiedPrompt + RAG→LLM 管线 + 分层路由) | 所有节点 prompt 质量提升 |
| **Batch 2** | P0-3/P0-7 (LLM→RAG 验证 + 输出校验) | 临床安全兜底 |
| **Batch 3** | P0-4/P0-5 (OpenAPI 管线 + Loop 三阶段) | 架构统一 |
| **Batch 4** | P1-8/P2-9/P2-10 (Harness 增强 + 缓存 + 溯源) | 体验优化 |

## 6. 技术决策

| 决策 | 选项 | 选择 | 理由 |
|------|------|:--:|------|
| RAG→LLM 注入方式 | prompt 拼接 vs function calling | **prompt 拼接** | 更可控、可调试、token 更少 |
| LLM→RAG 验证粒度 | 字段级 vs 段落级 | **字段级** (诊断/用药/剂量) | 减少误报 |
| RAG 分层路由 | 代码 switch vs 配置 | **配置** (`node_rag_map.yaml`) | 可调参 |
| OpenAPI 缓存 | Redis vs 内存 | **内存 LRU** (先) → **Redis** (后) | 阶段 0 减依赖 |
| CircuitBreaker 降级 | 规则引擎 vs 跳过卡点 vs 人工 | **规则引擎** → **人工** | 三档渐进 |
