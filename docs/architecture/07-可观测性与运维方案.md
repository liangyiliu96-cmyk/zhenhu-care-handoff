## 1. 日志规范

| 项目 | 规范 |
|------|------|
| 格式 | 结构化 JSON，每行一条 |
| 必含字段 | `timestamp`, `level`, `logger`, `request_id`, `service`, `message` |
| 上下文字段 | `case_id`, `actor`, `event_type`, `duration_ms`（按需） |
| 输出 | stdout（Docker 收集）；阶段 2 接入 ELK/Loki |
| 脱敏 | 日志中禁止记录患者 PII，`request_id` 替代 |

**参考 PoC：** PoC 无结构化日志 → 正式工程统一 `structlog` 库，FastAPI middleware 自动注入 `request_id`（参考 `main.py` 已实现的 `add_request_id`）。

## 2. 健康检查

每个服务暴露 `GET /health`，返回依赖连通性：

```json
{
  "status": "ok",
  "version": "0.2.0",
  "timestamp": "...",
  "dependencies": {
    "mysql": "ok",
    "redis": "ok",
    "milvus": "ok"
  }
}
```

| 服务 | 检查项 |
|------|--------|
| api-gateway | Redis（会话/JWT黑名单） |
| workflow-engine | MySQL（`zhenhu_workflow`） |
| knowledge-orchestrator | MySQL + Milvus + Redis（Celery） |
| fhir-adapter | MySQL（`zhenhu_fhir`） |

**参考 PoC：** PoC 的 `GET /healthz` 返回 `workflow_state` → 升级为依赖连通性检查，已实现在 `main.py` `/health` 端点，待补充 `dependencies` 字段。

## 3. 指标与告警

### 3.1 指标采集

| 指标 | 来源 | 用途 |
|------|------|------|
| 端点延迟（p50/p95/p99） | FastAPI middleware | 性能基线 |
| 错误率（按 HTTP 状态码） | FastAPI middleware | 异常检测 |
| 吞吐量（req/s） | FastAPI middleware | 容量规划 |
| Agent 调用耗时 | workflow-engine Agent 层 | LLM 成本监控 |
| Milvus 检索延迟 | knowledge-orchestrator `search.py` | 检索性能 |

阶段 0 用 FastAPI 内置 `prometheus_client`；阶段 2 接入 Grafana + Prometheus。

### 3.2 告警分级

| 级别 | 条件 | 响应 |
|------|------|------|
| **P0 紧急** | 任一服务不可达（health check 连续 3 次失败） | 立即通知 + 自动重启 |
| **P1 严重** | DB/Redis/Milvus 依赖降级（部分端点 503） | 15min 内响应 |
| **P2 关注** | p95 延迟超过基线 2x 或错误率 > 1% | 次日排查 |

## 4. 部署与 CI/CD

| 阶段 | 部署方式 | 说明 |
|------|----------|------|
| 阶段 0 | Docker Compose（5 容器） | `docker-compose.yml` 一键启动 |
| 阶段 2 | K8s + Ingress + 持久卷 | 各服务独立扩缩容 |

| 触发器 | 动作 | 工具 |
|--------|------|------|
| PR → main | `ruff lint` + `mypy` + `pytest` | GitHub Actions |
| PR + `e2e` label | 上者 + 集成测试 + E2E smoke | Playwright |
| main push | 全量测试 + Docker build + push registry | GitHub Actions |

**蓝绿部署：** 阶段 2 引入，新版本启动 → 健康检查通过 → 流量切换 → 旧版本保留 5min 回滚窗口。
