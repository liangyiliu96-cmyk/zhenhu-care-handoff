# 臻护前端功能设计文档 v0.16

> **原则**: 每一条线都必须落到 API。每个按钮都知道它调用什么、返回什么、怎么处理失败。
> **硬约束**: 1920×1080 基准分辨率, 最小 1366×768。不做平板/手机适配。
> **不写代码**, 只定接口、数据流、组件边界、状态流转。
> **v0.14 历史说明**: 曾提出品牌首页与三步凭证登录设想；v0.15 已按生产 OIDC、已注册 API 和临床工作流重新收敛。
>
> **v0.15 对齐原则（2026-07-19）**：本次只迭代设计文档，不创建前端工程。以下“后端事实优先”章节覆盖文档中与其冲突的早期设想；前端实现必须以已注册路由、认证中间件和响应字段为唯一真相，不能用 UI 假设替代临床数据、权限或审计链路。

## 零点五、v0.15 后端事实对齐与设计升级

### 0.15.1 已确认的交付边界

| 主题 | 当前后端事实 | 前端设计决策 |
|------|------|------|
| 认证 | 生产环境只允许 `AUTH_MODE=oidc`；工号密码登录生成的 JWT 仅适用于非生产 `AUTH_MODE=jwt` 场景。 | 生产登录页跳转医院 SSO；本地/联调环境才显示工号密码表单。登录后的身份以 `/inpatient/whoami` 与受保护接口的实际结果为准。 |
| 临床助手 | `/assistant/chat` 与 `/assistant/chat/stream` 要求已认证的 `actor_id`；登录身份负责授权，`assistant_mode` 负责选择能力。医生可用 `doctor/pharmacist/integrative/patient`，护士可用 `nurse/patient`，后端强制校验且会话模式不可中途切换。 | 前端按业务场景呈现查房、护理、用药、中西医协同和患教能力，不把助手模式伪装成登录角色。首页健康小助手只调用隔离的 `/assistant/public/*`，不接受 `patient_id`、不读取病历并受频率限制。 |
| SSE | 助手流式接口是 `POST /assistant/chat/stream`，且生产请求需要认证头。 | 使用 `fetch` + `ReadableStream` 解析 SSE，不使用 `EventSource`。中止用 `AbortController`；离开页面、切换患者或发送新问题时必须取消旧流。 |
| 临床证据 | 图内临床输出将引用保存在 `clinical_evidence`；`GET /inpatient/{id}/evidence` 返回患者级引用链；`POST /inpatient/{id}/query` 返回本次回答的 `citations`。 | EvidencePanel 首选患者级 `/evidence` 与回答级 `citations`，呈现来源、版本、片段和检索时间。`/inpatient/rag/search` 仅用于知识库探索，不能伪装为某个临床结论的直接证据。 |

| 告警生命周期 | `GET /inpatient/{id}/alerts`、`POST .../acknowledge`、`POST .../resolve` 已可用；写操作为医生权限且可带 `expected_version`。 | 告警不是本地“已读”状态。使用服务端 `status`、操作者、时间戳渲染，并在操作成功后更新患者、工作台和病区视图。 |

### 0.15.2 产品信息架构升级

临床产品的首屏不应是营销叙事后再进入工作流。改为“受控入口 + 工作入口”：未登录时以简洁品牌页、系统状态、SSO/联调登录入口和隔离的健康小助手为主；登录后直接进入医生工作台、护理任务台或管理台。健康小助手只能做一般健康、康复和复诊信息支持，不形成患者身份、不读取病历；处方外发、PDF 导出和“发送至患者”等未有受控后端闭环的能力不进入一期可点击导航。

医生端以**待审核、需要复核的告警、病区优先级**三类工作为第一屏。患者 Dashboard 以**当前风险、最新变化、下一步临床行动、证据来源**为第一阅读顺序，而不是九个面板平铺。护理端以**本班必须完成的任务**为唯一主队列，页面不将本地勾选伪装为已写入临床记录。

### 0.15.3 视觉方向升级

采用“安静的临床资料室”而非模仿任何医疗品牌：灰白纸面、墨蓝文字、青绿稳定色、琥珀复核色与朱红高危色共同承担语义。页面是连续的工作表面，不用营销式卡片瀑布、玻璃拟态、彩色渐变或装饰性数据泡泡。工作台保持紧凑但有明确留白：顶部 52px 上下文栏，左侧 208px 导航，中间任务区，右侧仅在需要证据、患者摘要或助手时打开的 360px 工具栏。

所有状态使用文字、图标和颜色三重表达；使用 Lucide 图标，不使用 emoji 作为医学严重程度编码。字体大小使用稳定的 rem 档位，不随视口宽度缩放；响应式只改变栅格与面板位置。临床写操作使用明确的命令按钮，图标按钮仅用于返回、关闭、筛选、刷新、展开等通用工具，并提供 tooltip。

### 0.15.4 一期禁止的假闭环

以下内容可以作为不可点击的“后续能力”说明，但不得在一期交互中显示为已完成的功能：

- 公开助手携带患者身份、`patient_id`、病历数据或进入临床写操作；首页仅允许隔离的一般健康问答。
- 本地完成护理任务、确认接班、告警升级后却不产生服务端记录的状态。
- 浏览器直接导出带临床审计承诺的 PDF、发送给患者/家属、处方外发。
- 使用 L15/L16 中医知识、RAG 来源卡或实时 SLA 时间戳，除非对应后端查询和可追溯数据已实际提供。

## 零、后端 API 契约全量清单 (基于代码审计, 非猜测)

> 这是设计文档的"地基"。前端每一个模块、每一个按钮、每一个导航都必须能在这张表中找到对应的 API。
>
> **版本化路由 (Codex v0.3)**: 以下 12 类端点同时存在于原始路径和 `/v1/` 前缀下:
> `/v1/inpatient/admissions`, `/v1/inpatient/monitoring/`, `/v1/inpatient/discharge/`, `/v1/inpatient/review/`,
> `/v1/inpatient/admissions/{id}/history`, `/v1/inpatient/{id}/command`, `/v1/patients`, `/v1/inpatient/{id}/rounds`,
> `/v1/inpatient/{id}/scores`, `/v1/inpatient/{id}/care/`, `/v1/inpatient/{id}/evidence`, `/v1/inpatient/{id}/alerts/`
> 前端可直接使用原始路径，无需修改。`/v1/` 路由为未来版本演进预留。
>
> **认证体系 (v0.15)**: 生产 OIDC，非生产联调模式
> - **生产 (`APP_ENV=production`)**: 仅 `AUTH_MODE=oidc`。前端跳转医院 SSO，回调后携带 IdP 签发的 Bearer token；不得展示或调用工号密码登录作为生产兜底。
> - **本地/联调**: `AUTH_MODE=header` 或 `AUTH_MODE=jwt` 可使用受控测试身份；`POST /inpatient/login` 仅在 `AUTH_MODE=jwt` 的非生产环境用于取得测试 JWT。
> - **身份真相**: 前端启动及会话恢复调用 `/inpatient/whoami`；角色、职称、科室和默认落点均以响应为准，不能用用户选择的角色、科室或请求头推断。
> - **权限边界**: doctor-only / nurse-shared 由 auth middleware 在每个请求上独立验证；前端守卫只用于减少误操作。

## 一、设计哲学

```
医生的屏幕不是仪表盘，是决策流水线:

  [告警条] → [待办队列: 按紧急度一项项处理] → [DiffPanel: AI vs 我]

     → [下一待办] → 队列清空 → ✅ 暂无待办
```

## 四、设计语言与交互规范

### 4.1 视觉风格关键词

| 关键词 | 含义 | 防AI化策略 |
|------|------|------|
| **克制而非冷淡** | 临床数据需要呼吸感 | 中性色带品牌蓝微染色(OKLCH chroma 0.01), 拒绝纯黑#000 |
| **层次即安全** | 信息密度按决策紧急度递减 | 模糊测试(Squint Test): 模糊后仍能识别告警→队列→数据的优先级 |
| **每个像素都有意图** | 不堆装饰 | 没有毛玻璃/多余阴影/渐变。AI标签必须有证据来源, 否则不显示 |
| **速度即尊重** | 医生不是在浏览, 是在工作 | 侧滑代替跳转, Enter代替点击, 预加载下一待办 |
| **包容不是妥协** | 从住院医到老主任都能用 | 固定 rem 字号档位、对比度≥AAA、键盘全操作 |

**反模式 (Anti-Patterns) — 明确避免**:
- ❌ Inter / Roboto / Open Sans 字体 → 临床产品需要更强的品牌辨识
- ❌ 毛玻璃面板 / 弥散阴影 → 增加认知负载
- ❌ 紫蓝渐变 / 霓虹点缀 / 青+深色配色 → "AI感"过重
- ❌ 卡片套卡片 / 万物皆圆角 → 边缘清晰有利于数据对比
- ❌ 纯黑 #000 / 纯白 #fff → 用 OKLCH 微染色中性色

### 4.3 关键交互模式

#### A. 侧滑面板 (Slide-over Panel)
```
适用: DiffPanel、证据详情
宽度: 520px, 遮罩半透明
关闭: 点击遮罩 / Esc / 面板外点击
嵌套: DiffPanel 内点 [证据▸] → 再滑出 EvidencePanel (z-index+1)
API 映射:
  DiffPanel: 数据来自 pending 项内的 payload
  EvidencePanel: GET /inpatient/{id}/evidence；回答内证据使用本次 /query 的 citations
```

#### B. 待办推进 (Queue Flow)
```
行为:
  1. 点击待办项 → DiffPanel 侧滑
  2. 完成决策 → POST /inpatient/review/{id} → 成功
  3. DiffPanel关闭 → 该待办从列表消失(滑出动画)
  4. 自动高亮下一待办 (GET /ward/pending 刷新)
  5. 队列清空 → "✅ 暂无待办"
```

#### C. 告警脉冲 (Alert Pulse)
```
高危: 朱红边线 + 明确文字标签；不使用闪烁动画干扰临床阅读。
关注: 琥珀色文字与图标标签。
时间: 仅呈现后端返回的创建、确认、解决时间；没有字段则不推断 SLA 或升级结果。
数据: GET /inpatient/{id}/alerts + POST acknowledge/resolve（医生权限、expected_version）。
```

#### D. 证据穿透 (Drill-down)
```
层级: AI结论 → 点[证据] → 患者级临床来源卡片 (GET /inpatient/{id}/evidence)
     → 点[原始数据▸] → 具体检验/体征值 (来自 dashboard)
动画: 逐层右滑, 面包屑导航可回溯
```

#### E. 滚动时间线动画
```
数据: GET /inpatient/{id}/timeline → events[]
动画: Intersection Observer + CSS @scroll-timeline
新事件 (轮询发现新 document_chain 条目): 从底部插入 + 绿色高亮渐隐(2s)
```

#### F. AI 源标签
```
样式: pill badge
  L1 临床评分 — bg oklch(95% 0.04 255)
  L2 疾病要点 — bg oklch(95% 0.04 255)
  L5 药物安全 — bg oklch(97% 0.06 80)
  L6 检验参考 — bg oklch(96% 0.03 280)
  L9 出院患教 — bg oklch(95% 0.05 160)
hover: 显示知识摘要, click: 展开 EvidencePanel
```

#### G. 键盘快捷键
```
Enter    → 确认当前操作 / 提交 DiffPanel
Esc      → 关闭侧滑面板
Tab      → 在 DiffPanel 的 AI 栏和医生栏之间切换
1-9      → 快速选择待办项第 N 项
/        → 聚焦 ChatBox 输入框
Ctrl+S   → 提交审核决策
```

#### H. 临床操作响应时间契约

| 操作类型 | 预期时延 | 前端反馈 | 超时 (>15s) |
|------|------|------|------|
| 页面初始加载 (Dashboard) | ≤ 2s 首屏, ≤ 5s 全量 | 骨架屏 (占位色 + 脉冲) | "加载较慢, 数据仍在传输中" banner |
| DiffPanel 提交 (POST /review) | ≤ 1.5s | 按钮锁 → spin → ✓/✗ | "提交中, 请勿关闭" + 不自动重试 |
| Command (转科/出院) | ≤ 2s | 确认弹窗 → [执行中] → 成功/失败弹窗 | 同上 + 保留用户输入 |
| SSE 聊天流 | 首 token ≤ 3s | 光标闪烁 + "正在检索..." | "检索超时, 请重试" + [重试] |
| 侧滑面板打开 | ≤ 150ms | ease-out 动画 | — (纯本地) |
| 列表滚动加载 | ≤ 200ms | 底部骨架行 | [加载更多] 按钮替代自动加载 |

**慢速网络降级**: 当连续 3 个请求超过 5s, 显示顶部黄色窄条 "当前网络较慢, 数据更新可能延迟", 但不禁用操作。

#### I. 动画规范
```
入场: 200ms ease-out, opacity 0→1 + translateY(4px→0)
出场: 150ms ease-in, opacity 1→0
侧滑面板: 250ms cubic-bezier(0.4, 0, 0.2, 1)
数字变化: 不滚动动画 → 直接替换 (避免误读)
加号/新增: 绿色边框闪烁 1s 后稳定 (不播放弹跳)
禁用: @media (prefers-reduced-motion: reduce) 时全部 instant
```

### 4.4 AI 助手交互模式

#### ChatBox 三模式完整规格

```
┌─ 模式 1: 浮动模式 (Floating) ─────────────────────────
│  触发: 右下角 48×48px 圆形按钮 (fixed, z=1000)
│        /workbench、/nurse、/patient/:id → 单个 Lucide MessageSquare 按钮
│  尺寸: 380×520px, 从右下角滑入
│  Role: 由已认证服务端会话决定；前端不传 role
│  PatientId: 当前页面的 patientId 自动注入
│  关闭: 遮罩点击 / Esc / 关闭按钮
│
├─ 模式 2: 侧栏模式 (Sidebar) ─────────────────────────
│  触发: Dashboard 页面加载时自动渲染
│  位置: RightCol 内, 360px 固定宽度, 跟随页面滚动
│  Role: 由已认证服务端会话决定
│  PatientId: 当前 dashboard 患者
│  Compact: true (简化 header, 消息区 h=320px)
│
├─ 模式 3: 内嵌模式 (Inline) ──────────────────────────
│  触发: 出院小结 ChatBoxInline；公开首页不提供 ChatBox
│  尺寸: 全宽容器, h=180px（出院）
│  Role: 由已认证服务端会话决定
│  PatientId: 当前患者（出院）
│  Compact: 是 (不显示 session 信息, 不显示 health 指示灯)
│
└─ 三模式共享的 Props ────────────────────────────────
   patientId?: string    // 注入患者上下文 (db_enabled 角色)
   compact?: boolean     // 简化 UI (省 session health 等辅助信息)
   onClose?: () => void  // 浮动模式关闭回调
```

#### ChatBox 内部状态

```
Messages[]:
  每条消息:
    { role: "user"|"assistant", content: string, timestamp: string,
      sources?: [{layer, topic, text}],    // AI 回答的来源引文
      health?: {rag: "ok"|"error"|"fallback", llm: "ok"|"error"},
      confidence?: number,                  // 0-1 置信度
    }

Session:
  前端本地: 消息历史 + sessionId (uuid.hex[:12])
  后端持久: Redis key asst:{sid}, TTL 1800s
  健康状态: 仅在 SSE 事件确实返回 health 时呈现文字+图标状态；不自行推断 RAG 或 LLM 可用性。

流式渲染:
  SSE event data → 逐 token 追加到最后一个 assistant 消息
  渲染完成后追加 sources + health 信息
```

#### 预设问题按钮
```
API: GET /assistant/quick-questions?role=<whoami.role>
问题分 3 类: 临床操作 | 数据解读 | 知识查询
显示为可点击 chip 标签, 点击即发送
```

#### 助手返回内容展示
```
每条 AI 回答下方:
  sources: [{layer, topic, text}] → [L2] 冠心病诊治要点 [查看▸]
  health: {rag, llm, session} → 仅在服务端提供时显示健康状态
  置信度: 0.85 → 进度条 85% 蓝色
```

### 7.2 统一 API Client、并发与跨视图刷新

```typescript
apiClient: {
  // 读取 user identity 后决定请求认证方式；不允许页面自行拼装权限头
  auth: oidcOrJwt ? { Authorization: `Bearer ${token}` } : controlledDevHeaders,
  // header 模式的测试身份由受控环境注入，页面与组件不得根据 user 自行拼接身份头。
  requestId: crypto.randomUUID(),
  mutation: {
    // 每次临床写入生成新 Idempotency-Key；网络重试必须复用同一个 key
    idempotencyKey: crypto.randomUUID(),
    // 对患者状态有影响的请求从 patientStore 读取，不由表单自行维护版本号
    expectedVersion: patientStore.currentPatient?.state_version,
  },
}
```

**统一响应处理**：读取 `UnifiedResponse.data`；任何 `error.code` 都进入错误分支，即使 HTTP 状态仍为 2xx。`401` 清除内存身份并跳转 SSO/登录入口；`403` 显示“无该患者/功能访问权限”且不泄漏患者摘要；`404` 仅显示不存在，不尝试创建；`409 STATE_VERSION_CONFLICT` 进入冲突处理；`5xx` 可重试读取但不自动重试临床写入。

**409 冲突处理**：保留本地草稿、禁用提交、并行重新获取 Dashboard、照护管理、告警或待审核项。若目标记录已由他人处理，明确显示“已由其他临床人员更新”，提供“查看最新状态”和“以当前数据继续编辑”两个动作；不以旧表单自动覆盖服务端数据。

| 临床动作 | 成功后必须失效/刷新 | 不得做的事 |
|------|------|------|
| 提交审核 | 待审核队列、患者 Dashboard、timeline、scores、evidence、病区患者列表、alerts | 本地直接删除待办后不确认服务端返回的新 checkpoint |
| 上报体征/检验 | Dashboard、trends、scores、alerts、nurse tasks、ward overview | 乐观添加趋势点并假设图已完成推理 |
| 告警确认/解决 | 患者 alerts、Dashboard、病区 alerts、timeline | 仅修改浏览器中的状态标签 |
| 医嘱/MDT/宣教/随访 | care-management、Dashboard、timeline、待审核队列 | 409 后用旧版本重试写入 |
| 交接签收 | discharge summary、Dashboard、timeline | 把“按钮被点击”显示为“交接已完成” |

**证据缓存边界**：患者级证据与提问级 citations 按 patient id / question request 生命周期缓存；当监测、审核、用药或检验写成功后，失效当前患者的 evidence query。全局 RAG 搜索结果只能作为短时探索缓存，不能覆写患者级证据链。

## 八、状态机定义

### 8.1 DiffPanel 状态机

```
States: IDLE | LOADING | READY | DIRTY | SUBMITTING | SUCCESS | CONFLICT | ERROR

Transitions:
  IDLE        --(待办点击)-->  LOADING
  LOADING     --(数据就绪)-->  READY
  LOADING     --(超时10s)-->   ERROR
  READY       --(用户操作)-->  DIRTY
  DIRTY       --(撤销操作)-->  READY (所有操作还原)
  DIRTY       --(点击提交)-->  SUBMITTING
  SUBMITTING  --(API 200)-->   SUCCESS
  SUBMITTING  --(API 409 STATE_VERSION_CONFLICT)--> CONFLICT (保留草稿并刷新目标数据)
  SUBMITTING  --(其他 API 4xx)--> ERROR (显示错误消息)
  SUBMITTING  --(API 5xx)-->   ERROR (显示"服务器错误")
  SUCCESS     --(500ms后)-->   CLOSED (从 store 移除, 关闭面板)
  CONFLICT    --(查看最新状态)--> READY
  CONFLICT    --(以当前数据继续编辑)--> DIRTY
  ERROR       --(点击重试)-->  SUBMITTING
  ERROR       --(点击取消)-->  READY

Guard: [✗]选中 + 理由 < 10字 → SUBMITTING 禁止
```

### 8.2 待办队列状态机

```
States: LOADING | HAS_ITEMS | EMPTY | ERROR

Transitions:
  LOADING   --(API 200 + items.length>0)--> HAS_ITEMS
  LOADING   --(API 200 + items.length=0)--> EMPTY
  LOADING   --(API 失败)-->               ERROR (保留缓存)
  HAS_ITEMS --(最后一项提交成功)-->         EMPTY (动画过渡)
  HAS_ITEMS --(API 刷新失败)-->            HAS_ITEMS (显示非关键错误横幅)
  EMPTY     --(API 刷新有新增)-->           HAS_ITEMS (动画滑入)
  ERROR     --(重试成功)-->               HAS_ITEMS 或 EMPTY
```

### 8.3 ChatBox 状态机

```
States: IDLE | STREAMING | ERROR

Transitions:
  IDLE       --(发送消息)-->   STREAMING
  STREAMING  --(SSE 完成)-->   IDLE
  STREAMING  --(SSE 错误)-->   ERROR
  ERROR      --(重试)-->       STREAMING

内部数据流:
  用户输入 → POST /assistant/chat/stream → SSE events:
    data: {"token": "..."}        → 追加到消息

```

### 8.4 告警生命周期状态机

```
States: UNACKNOWLEDGED | ACKNOWLEDGED | RESOLVED

服务端持久化:
  UNACKNOWLEDGED --(POST /inpatient/{id}/alerts/{aid}/acknowledge, expected_version?)--> ACKNOWLEDGED
  ACKNOWLEDGED   --(POST /inpatient/{id}/alerts/{aid}/resolve, expected_version?)-->    RESOLVED

前端规则:
  - 只有医生权限且接口返回允许操作时展示确认/解决命令。
  - 成功后以 GET /inpatient/{id}/alerts 返回的 status、操作者和时间戳为准，并刷新患者页、工作台和病区视图。
  - 409 STATE_VERSION_CONFLICT 时保留当前备注，刷新告警及患者 state_version 后由用户重新确认；禁止自动重放。
  - 不以本地计时器升级告警，也不展示后端未提供的 SLA 时钟。
```

## 九、全局错误处理与空态策略

### 9.1 错误分级与处理

| 级别 | 场景 | 处理 | 示例 |
|:--:|------|------|------|
| L1-Fatal | 页面核心数据加载失败 (dashboard, pending) | 页面级错误横幅 + [重试] 按钮 | "⚠️ 数据加载失败，请检查网络后重试" |
| L2-Error | 非核心模块加载失败 (ai-summary, insights) | 模块隐藏 + toast 通知 | "AI 摘要暂不可用" (toast, 3s 消失) |
| L3-Warn | 网络超时、API 降级 | toast (warning) + 不阻断操作 | "请求超时，已使用缓存数据" |

**全局错误边界 (React Error Boundary)**:
- 顶层 `<ErrorBoundary>` 包裹整个 App
- 崩溃时渲染: "系统异常" + [刷新页面] + 错误日志上报
- 不崩溃页面级组件 (如 DiffPanel 崩了不影响工作台)

**Toast 系统**:
- 位置: 右上角固定, z=2000
- 类型: success (绿) / error (红) / warning (黄) / info (蓝)
- 自动消失: 3s (success/info) / 5s (warning) / 手动关闭 (error)
- 最多同时显示 3 条, 超出队列 FIFO

  开发环境: AUTH_MODE=header 或 AUTH_MODE=jwt，仅使用受控测试身份；不提供任意角色切换 UI
    前端行为: header 模式由受控开发环境注入身份；jwt 模式通过联调 LoginModal 登录后查询 whoami
  生产环境: OIDC Bearer token (AUTH_MODE=oidc + JWKS)
    前端行为: 跳转医院 SSO 登录页 → 回调带 token → 设 Authorization header → 查询 whoami
  角色 enforce: review/command/discharge → doctor-only; ward/nurse/monitoring → shared

用户管理:
  - 注册: 不支持。用户由管理员批量导入 (POST /inpatient/org/seed)
  - 密码: 不涉及。依赖医院统一身份系统 (OIDC/SSO)
  - 会话: auth middleware 每个请求独立验证 Bearer token, 无服务端 session
  - 前端本地: authStore 在内存中保存当前 user identity, 无持久化 token
```
