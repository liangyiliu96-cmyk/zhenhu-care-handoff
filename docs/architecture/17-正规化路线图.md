## Phase 0 · 工程地基(立即可做,1–2 周)

### 目标
解决 15 号文档 **G1(CI/CD)、G6(lint/锁定)、G4 部分(密钥)**。

### 任务
| ID | 任务 | 产出 | 验收标准 |
|---|---|---|---|
| P0-1 | 搭建 CI/CD 流水线(GitHub Actions 或 GitLab CI):PR 触发 → 后端 4 服务 pytest(含契约)→ 前端 vitest + tsc + eslint → playwright 冒烟 → 镜像构建 → 镜像推送 | `.github/workflows/ci.yml` + `docker-compose.ci.yml` | 任一 PR 全绿;镜像带 git SHA tag |
| P0-2 | 后端统一 lint/format/type check:引入 ruff(+format)+ mypy(或 pyright);前端已有 eslint,补 `npm ci` 锁定 | 各服务 pyproject 增 `[tool.ruff]`/`[tool.mypy]`;新增 `requirements-dev` 或 uv | `ruff check && mypy` 零错误进 CI |
| P0-3 | Python 依赖锁定:改用 uv/poetry 生成 `uv.lock`/`poetry.lock`;前端补 `apps/frontend/package-lock.json` 并 Dockerfile 改 `npm ci` | 锁文件 + Dockerfile 修改 | `pip install -r requirements.lock` 可复现构建 |
| P0-4 | 密钥/配置管理:`.env` 全部换强随机密码;compose 改为 `${VAR:?required}` 强制注入;引入 `.env.staging` 模板;CI 用 secrets | `.env.example` 更新 + compose 加固 | 无默认弱密码;密钥不进 git |
| P0-5 | 文档基线:补充 CONTRIBUTING/部署手册/回滚手册 | `docs/` 新增 | 新成员可按文档独立部署 |

### 风险
- 引入 lint/mypy 会暴露存量问题 → 设 `warn` 起步,限期清零;
- CI 首次接 MySQL 集成测试耗时 → Phase 0 先跑 SQLite 快速门禁,MySQL 集成测试进 Phase 1。

## Phase 1 · 安全与数据治理(1–2 月)

### 目标
解决 **G2(认证网关)、G3(结构化日志/metrics)、G4(迁移/Milvus)、G7(TLS/加密)、G9(审计)、G10(集成测试/备份)**。

### 任务
| ID | 任务 | 产出 | 验收标准 |
|---|---|---|---|
| P1-1 | API 网关(建议 Python/FastAPI 或 Kong/APISIX):统一认证(JWT/OIDC)、路由、限流、请求审计 | 新服务 `api-gateway`(README 已有占位) | 全部 4 服务仅经网关可达;未认证请求 401 |
| P1-2 | 全服务接入认证:workflow/knowledge/fhir 复用 inpatient-ward `auth.py` 模式(OIDC 优先);接入真实 IdP(Keycloak 容器) | 4 服务统一 AUTH_MODE=oidc | 生产模式启动强制 OIDC;角色矩阵生效(参照《分角色功能权限矩阵》) |
| P1-3 | 结构化日志 + metrics 全面铺开:把 `observability.py` 提升为共享契约包 `zhenhu.contracts.observability`,4 服务统一 JSON 日志 + `/metrics`;prometheus 增加 4 个 target;告警 webhook 接真实通道(企业微信/钉钉/SMS) | contracts 包 + compose 监控更新 | 4 服务 /metrics 可被 Prometheus 抓取;线上 5xx/延迟告警可达人 |
| P1-4 | 数据库迁移体系:Alembic 落地 4 服务(workflow/knowledge/fhir 从 create_all 迁移到 Alembic 基线;inpatient-ward 自研迁移器迁移至 Alembic 或保持并文档化) | 4 服务 `alembic/` + `alembic upgrade` CI 验证 | 空库 `upgrade head` 成功;`downgrade` 可回滚 |
| P1-5 | Milvus 部署落地:compose 增 Milvus Standalone(Milvus Lite 嵌入式为备选,当前已落地 Standalone);knowledge-orchestrator 检索切换向量(复用 inpatient-ward rag_engine 模式) | compose milvus 服务 + knowledge 向量检索 | RAG 检索在容器环境实测可用;LIKE 检索保留为降级 |
| P1-6 | MySQL 集成测试进 CI:用 ephemeral MySQL 容器跑 `test_mysql_integration.py` + 新增 workflow/knowledge/fhir 的 MySQL 集成用例 | CI job `mysql-integration` | 三库在 MySQL 上建表/迁移/事务全绿 |
| P1-7 | TLS 与静态加密:nginx 加证书(自签→生产 CA);MySQL 开启 TDE(或明确密钥管理);强制 HTTPS | nginx.conf + MySQL 配置 | 全链路 HTTPS;无明文落盘 |
| P1-8 | 审计补全:workflow/knowledge 加审计日志(复用 `audit.py` 模式);审计表独立 schema/独立账号;定义保留期(≥6 年) | 审计模型扩展 + 保留策略 | 所有患者数据访问可审计到"谁/何时/看了哪些患者" |
| P1-9 | 备份恢复:MySQL 定时备份(mysqldump/xtrabackup)+ 恢复演练脚本;定义 RPO/RTO(目标 RPO≤24h,RTO≤4h) | `scripts/backup*.sh` + 演练记录 | 恢复演练通过,数据可还原 |

### 风险
- 认证网关改造会破坏现有前端调用 → 网关先做"透传+鉴权"两阶段,前端 header 兼容期保留;
- Alembic 迁移与自研迁移器并存风险 → 统一为 Alembic 单轨(见 P1-4);
- Milvus 内存占用 → 生产建议独立节点或量化模型(MiniLM 384 维已较轻)。

## Phase 2 · HIS 互操作 + 可观测完整落地(2–4 月)

### 目标
解决 **G8(真实 HIS 对接)、FHIR 互操作成熟度(15 号 §7)** + 可观测补全(tracing/日志采集)。

### 任务
| ID | 任务 | 产出 | 验收标准 |
|---|---|---|---|
| P2-1 | 部署 HAPI FHIR + OpenMRS 仿真环境(compose profile `his-sim`) | compose 扩展 | 一键拉起仿真 HIS |
| P2-2 | fhir-adapter 互操作层升级:标准 FHIR R4 客户端(httpx)、`_lastUpdated` 增量引擎、`$export` 全量初始化、Idempotency-Key 全写路径、MPI 映射表与匹配服务、Consent 决策流 | fhir-adapter 扩展模块 + `mpi_mapping` 表 | 达到 16 号 §5 验收标准 1–7 |
| P2-3 | 双向同步业务打通:Patient/Encounter/Observation/Condition/MedicationRequest/CarePlan/Consent 映射(含 LOINC/ICD-10/国内编码映射) | 映射配置 + 同步引擎 | 臻护出院计划可回写 HIS;HIS 检验/医嘱变更驱动臻护临床状态更新 |
| P2-4 | 可观测性补全:OpenTelemetry tracing(跨 4 服务 + HIS 调用);Loki/ELK 日志集中采集;Grafana 大盘(业务/技术) | OTEL + 日志栈 + 大盘 | 一次跨服务请求可全链路追踪;告警有大盘可查 |
| P2-5 | 压测与性能基线:Synthea 生成仿真数据,压测同步引擎与查询;产出 P95 指标 | 压测报告 + 基线 | P95 查询 <500ms;同步窗口满足 16 号 §5 |

### 风险
- 真实医院 HIS 多数非 FHIR 原生 → 同步引擎须设计"适配器 SPI"(FHIR 适配器 / HL7 v2 适配器 / SQL 只读适配器),Phase 2 先验证 FHIR 通道;
- 数据一致性:双向写冲突 → 单一权威源原则(患者/就诊/检验/医嘱以 HIS 为准;照护计划/随访以臻护为准),冲突人工队列兜底;
- MPI 误匹配 → 高置信度才自动合并,其余人工。

## Phase 3 · 规模化与合规(长期)

### 目标
解决 **G5(K8s)、多租户/多院区、等保与医疗器械软件合规、灾备**。

### 任务
| ID | 任务 | 验收标准 |
|---|---|---|
| P3-1 | K8s/Helm:4 服务 + 中间件 Chart 化;ConfigMap/Secrets;HPA 与资源配额;滚动/蓝绿发布 | Helm 部署一键;升级零停机 |
| P3-2 | 多租户/多院区:租户维度数据隔离(库/表/行级)、院区标识贯穿审计与 MPI | 双院区并行运营数据隔离正确 |
| P3-3 | 合规:等保 2.0 三级定级与整改、PIPL 影响评估(DPIA)、医疗器械软件(若申报)文档体系、第三方依赖 SBOM 与 CVE 常态化扫描 | 通过等保测评;SBOM 随发布 |
| P3-4 | 灾备:跨机房/云容灾、RPO≤1h/RTO≤30min 演练、混沌工程(故障注入) | 年度灾备演练报告通过 |

### 风险
- 等保/器械合规周期不可控 → 提前立项并行;
- K8s 运维成本 → 若团队规模小,可评估托管 K8s 或维持 compose+监控(降级选项)。
