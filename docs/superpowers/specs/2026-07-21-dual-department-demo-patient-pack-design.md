# 心内科与呼吸科演示病例包设计

## 目标

用一套可重复重置的虚构临床病例，替换当前运行库中混杂的历史演示状态。心内科和呼吸科各提供 10 名患者，使医生工作台、护理工作台和统一管理端从同一后端状态源展示一致、可操作的病例。

本设计仅处理带演示标识的运行时病例及其关联工作流状态；不清理知识库、组织、模板、真实业务数据或数据库结构。

## 使用场景与成功标准

- 医生端能按科室看到 10 名对应患者，进入详情后可展示入院、监测、查房、审核、出院或随访上下文。
- 护理端能看到同一批患者中的护理任务、监测逾期、风险提醒和交接事项。
- 管理端的病区看板、待审核、预警、随访总览与模板/运维区域均使用相同状态源，统计数与患者明细一致。
- 每次执行重置后，两个科室各为 10 名病例，病例标识、状态分布和关键临床数据固定，便于复现演示和自动化测试。
- 旧运行库中的非演示患者不会被通配删除；旧的已知演示数据会通过受控迁移清理，避免继续污染页面。

## 病例矩阵

所有姓名、住院号、手机号码、联系人和地址均为虚构演示信息，并在患者状态中写入 `demo_seed: true`、`demo_pack_version`、`demo_department`。

## 架构与数据流

1. 在现有 `patient_fixtures` 旁建立集中式演示病例目录，按病例声明人口学信息、联系方式、科室、模板、病史、过敏史、生命体征、检验、医嘱、护理、查房、审核、出院和随访状态。
2. 由一个服务层将病例目录转换为当前状态存储契约。所有状态均保留 `department`、`phase`、`risk_level`、`state_version` 和演示元数据，避免前端特殊分支。
3. 新增受控的管理端重置接口。其步骤为：校验管理权限与非生产环境，定位带 `demo_seed` 标记或受控旧 fixture ID 的记录，清理对应的患者状态、工作流投影、待审核/随访投影与 Agent Loop 状态，再写入 20 例新状态。
4. 重置在单次请求内返回成功数、失败明细、按科室统计和病例版本；单例失败不应悄然吞掉，且不对非演示记录做降级清理。
5. 管理端运维区提供“重置演示患者”命令，显示影响范围，要求二次确认。前端调用新接口后刷新病区、护理、随访与医生看板查询缓存。

## 权限、环境与安全

- 接口必须复用现有管理操作授权与审计机制，只允许管理端角色执行。
- 在 `APP_ENV=production` 时拒绝执行；开发和演示环境允许执行。
- 管理端确认框明确告知将重置 20 名虚构演示患者及其相关工作流状态。
- 采用固定、显然虚构的个人信息，不写入真实联系方式，也不调用外部短信、CDS 或 FHIR 出站服务。
- 清理逻辑按元数据和固定旧 fixture ID 白名单定位，严禁截断共享状态表。

## 前端契约

- 不新增独立的患者列表数据源；医生、护理和管理端继续使用已有患者/病区/随访接口。
- 管理端只增加一个受权限控制的运维操作及结果反馈。其余页面根据已存在的状态字段自然显示病例。
- 进入患者详情后，各模块必须能处理完整病例和不完整病例，保留当前加载、空态和错误态，不得把演示状态写死在组件中。

## 验收与测试

1. 重置后状态存储中仅保留新版本的 20 个演示病例；旧 `demo-dashboard-care`、历史 `PATIENTS` fixture 及相关演示状态不再出现在三端查询中。
2. 心内科、呼吸科分别返回 10 名演示患者，角色/科室访问控制仍生效。
3. 医生、护理、管理端 API 各抽查至少一名高风险、待审核、待交接和异常随访患者，明细与看板聚合一致。
4. 重置接口拒绝非管理角色、生产环境和缺少确认语义的请求，并输出可审计事件。
5. 重复执行重置保持幂等：患者数、状态版本、看板统计和病例 ID 不累积。
6. 覆盖后端单元/路由测试、前端服务测试与浏览器流程：管理端重置后刷新三端页面，确认无请求错误、空白面板或失效患者链接。
