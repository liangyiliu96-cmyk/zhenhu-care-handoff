# 医生临床副驾驶一期设计

**范围**：医生端患者工作区，覆盖查房前预读、病史缺口引导和增量病程草稿。

## 目标

把已存在的患者事实、规则结果和已确认记录组织为医生可核对的下一步，不让模型替代诊断、医嘱、签字或出院决定。医生只需确认、编辑或补充，而不是反复翻阅和重写。

## 非目标

- 不创建自动医嘱、自动会诊、自动签字、自动出院。
- 不启用 `GRAPH_MODE=stateful`，继续使用已运行的 classic `PatientAgentLoop`。
- 不把自由文本或 RAG 内容直接写入正式病历。

## 用户流程

1. 医生打开患者的“查房”专区。
2. 系统读取当前 state version 下的体征、检验、告警、未审核事项、上次经医生确认的查房记录和入院病史。
3. 后端生成只读“查房前预读”：新出现或仍未解决的事实、需要核实的问题、病程草稿是否可生成。每项都给出事实来源和时间。
4. 医生可生成增量 SOAP 草稿。草稿只能使用事实快照中的原始数据；没有足够支持的段落必须标记“待补充”，不能由模型填充。
5. 医生在现有查房编辑器中修改并核对草稿，正式写入仍调用既有 round edit/review 链路。
6. 医生打开病史录入时，系统展示病种模板要求而当前未记录的项目。医生自行填写，提交仍调用既有 history endpoint。

## 架构

新增一个事实快照服务，不将提示词、页面或 LLM 当作事实来源。它输出：

- `facts`：带 `source_type`、`source_id`、`observed_at`、`field`、`value` 的原始事实。
- `attention_items`：确定性规则产生的待关注事项。
- `history_gaps`：按病种模板和既有病史计算的缺口，不由 LLM 推测。
- `progress_note_draft`：由快照驱动的增量 SOAP 草稿；LLM 可润色结构，Harness 必须删除不受支持的声明。

路由在 `patient_state_service.read()` 后生成快照，不增加独立持久化副本。每次响应都带 `state_version`，写入仍使用现有 optimistic lock。前端仅显示该版本的草稿；刷新后重新获取，不能自动重放旧草稿。

## 事实与幻觉控制

1. 原始患者数据、规则结果、医生已确认记录优先于 RAG 和模型文本。
2. 每个预读项与草稿段落都返回至少一个事实引用；无事实引用时只能返回“待补充”。
3. 模型只允许重写 `supported_facts`，不接收完整无边界病历，不允许生成诊断、剂量或处置结论。
4. 使用结构化 schema、字段长度限制、时间排序和输入版本校验。
5. LLM 失败、超时、无 RAG 或 Harness 校验失败时返回确定性草稿，不阻断查房或病史录入。
6. 草稿不会自动提交；医生编辑、保存和核对沿用已有审计事件。

## 界面

- 查房顶部新增“查房前预读”，按“新增事实 / 待核实 / 可生成文书”三组展示。
- 新增“生成增量病程草稿”按钮；生成后复用现有 SOAP 编辑与核对，不新建第二套正式病历界面。
- 病史录入弹窗增加“待补充信息”侧栏或分组提示，提示不会阻止自由录入。
- 显示来源标签和时间；没有来源时显示“待医生补充”，不显示伪引用。

## 验收标准

- 预读仅包含当前患者、当前 state version 的事实，且不跨患者泄露。
- 无新事实时明确显示“暂无新的结构化变化”，而非生成泛化总结。
- 生成草稿不改变患者状态；只有现有编辑/核对操作会更新状态。
- LLM 不可用时，规则预读、病史缺口和确定性草稿仍可用。
- 前端可从查房和病史入口完成全流程，所有按钮有真实接口或禁用原因。
