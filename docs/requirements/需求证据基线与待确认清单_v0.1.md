# 需求证据基线与待确认清单

**适用对象：** 《AI 出院交接与慢病随访协同平台需求规格说明书》  
**目的：** 将需求中的陈述分为已验证约束、候选实现能力、参考设计和待业务确认假设，避免将开源项目宣传、原型行为、参考文档或工程推断误写为医院上线要求。

## 1. 结论使用规则

| 级别 | 含义 | 在需求文档中的写法 |
| --- | --- | --- |
| A. 已验证约束 | 可在法规、规范或官方原文中直接核验 | 使用“必须/不得/应当”，并保留来源 |
| B. 已验证候选能力 | 可在本地开源仓库的源码或文档中核验 | 使用“可借鉴/候选方案”，不等同于选型或验收承诺 |
| C. 产品设计假设 | 为满足业务目标提出，或可从参考设计中吸收，但尚未有医院确认或实测验证 | 使用“拟/建议/待确认”，不得视作既定规则 |
| D. 未知或外部决策 | 需要医院、临床、信息安全、法务或伦理方决定 | 进入试点前待确认清单，不能由技术方案替代决策 |

## 4. 产品设计假设（C）

以下内容保留在 v0.2，但均需要试点验证：

- 首期采用五类 Agent：任务规划、病历一致性、指南合规、自检、审核与随访编排。
- 每条临床提示至少展示一条来源引用；无引用内容只能进入人工核实队列。
- 首期 FHIR 映射优先覆盖 `Patient`、`Encounter`、`Condition`、`AllergyIntolerance`、`Observation`、`DiagnosticReport`、`MedicationRequest`、`CarePlan`、`Task`、`Consent`、`Provenance`、`AuditEvent`。
- 工作流使用独立 `case_id`，并保存输入快照、节点状态、人工决定和发布状态。
- 系统默认以规则校验、结构化查询和 RAG 为先，Agent 仅处理无法由前述确定性路径安全完成的归纳和草拟任务。
- AI 协同服务以独立服务和版本化接口接入医院业务系统；知识原件、知识索引、工作流/审计和缓存/队列采用逻辑隔离，缓存不是事实来源。这是从《AI智参项目》2.1、2.3 和 7.3 的架构/数据流设计中吸收的工程假设，尚未与本院部署和数据治理方案核验。
- 路由先走确定性规则和结构化查询，再走 RAG、受控工具和 Agent；工具调用记录参数摘要和结果，低证据、高风险、失败或人工要求复核时升级人工。这是从《AI智参项目》4.4 和 6.6 的设计中吸收的安全路由假设，具体阈值和升级 SOP 待医院确认。
- 混合检索以单嵌入模型、全文检索和重排序建立首期基线；多嵌入模型、RRF 融合、双向量集合、知识图谱只在本项目评测集证明增益后再引入。参考来源为《AI智参项目》3.4；其中模型、维度、权重和性能提升数字未经独立验证。
- 受控汇总分析、患者端健康科普、语音交互与跨 Agent 长期记忆不进入 PoC；如后续立项，必须单独完成用途、数据流、权限、脱敏、人工升级和评测设计。参考来源为《AI智参项目》5.3、6.6、6.9 和 12；不构成当前需求承诺。
- 医护协同助手作为已登录工作台的受控入口进入 PoC；院内知识问答作为阶段 1 候选；患者端机器人维持阶段 3 独立立项。这是基于现有 CDSS 边界、网信办公开服务规则和本地参考项目作出的分期假设，尚待医院确认服务对象、知识域、人工队列和评测集。
- 知识文件采用显式生命周期，已发布版本在新版本处理失败时继续可检索；缓存按权限、病例、知识版本和输出契约隔离并在状态变化时主动失效；Agent 输出经服务端 Schema 校验后才可进入工作流。这些是从《AI智参平台实训教程 v3.2》吸收的工程设计假设，仍需在本项目 PoC 用例中验证。
- 助手、知识资产、工具和病例/FHIR 资源的有效权限取交集；患者端使用独立门户与最小 FHIR 资源范围；服务主体代表用户时需双重留痕。这是基于 FastGPT 与 Medplum 的实现资料形成的产品设计假设，尚待医院确认权限矩阵、患者关系与服务账号制度。

- PoC 病例与任务采用显式状态机，医生仅进行模拟确认，任务只可进入模拟发布状态；输入快照保留来源、时间、映射版本和冲突信息，Agent 冲突或部分失败不得被静默合并。这些机制须以预置的 PoC 案例验证，真实发布的责任和状态规则仍待医院确认。
- 临床引用以文档、版本、原文位置、分块、原文片段和检索策略构成不可变审计证据；已引用知识在失效、撤回或替代后会阻止在办病例继续发布，历史输出保留并标记失效。此行为是工程治理假设，临床复核范围仍待医院确认。
- 提示词、模型、规则、检索策略和输出契约采取版本化变更、测试基线、具名审批、受控发布与回滚；审计的完整性、时间源和紧急访问不以 PoC 实现替代医院制度。这是为保证可追溯性提出的产品设计假设，须在 PoC 和真实试点前分别验证与确认。
