# AI 出院交接与慢病随访协同平台

## 需求规格说明书 v0.2

**状态：** PoC 架构设计基线已确认；真实医院试点条件待确认  
**产品定位：** 面向医护人员的临床决策支持系统（CDSS）。系统通过受控知识库和多 Agent 工作流，发现出院交接与院后随访中的信息缺漏、冲突和规范风险；所有临床结论、病历改写和任务发布均须由具有相应权限的医护人员确认。

**证据状态：** 本文中的法规约束、候选开源能力、参考设计和业务假设已分离，详见《需求证据基线与待确认清单 v0.1》。开源项目和《AI智参项目》只作为候选实现或设计参考，不表示已完成技术选型、性能验证或合规认证。

| 工程边界 | AI 能力以独立服务和受控接口接入；不直连或共享医院生产业务库，不绕过现有身份、权限和审计边界 |

PoC 不是临床生产系统，不用于真实诊疗决策，不对患者发送建议，也不作为任何上线合规或临床有效性的证明。

| --- | --- | --- | --- |
| 阶段 0：PoC | 使用模拟或脱敏数据，跑通 RAG 引用、Agent 编排、医生确认模拟、交接单与随访任务草稿、审计记录；医护协同助手仅作为已登录 PoC 工作台的任务入口 | 本文第 0 节的 PoC 基线已具备 | 端到端演示可复现；每项提示可追溯到输入和知识来源；失败时明确降级 |

| 阶段 3：规模化协同 | 扩展至更多病种、科室和接收机构，逐步引入 MDT 协同、区域转诊或更多 FHIR 资源；患者端流程引导、健康科普或语音交互仅可作为独立候选课题 | 单院生产运行稳定，形成可复用数据契约和知识审核机制 | 各新增场景独立完成临床、数据、安全和运维验收，不因前一场景通过而自动放行 |

所有阶段均禁止自动诊断、自动开医嘱、自动修改病历或绕过医护审核向患者发布医疗处置建议。阶段 1 至阶段 3 的具体时间、病种、阈值和上线范围由医院确认后另行制定，不在本需求文档中预先承诺。

本演示剧本当前已有浏览器截图、API 冒烟和测试结果归档；后续如演示路径发生变化，必须同步更新测试用例、验证结果和本需求文档。

## 1. 目标与边界

### 1.1 首期目标

1. 在患者出院前，对出院小结、医嘱、检验结果、诊断、过敏史和既往记录进行一致性核验。
2. 根据经审核的临床指南、院内制度和随访 SOP，输出可回溯的风险项与交接建议。
3. 由医生确认后生成交接单草稿和院后随访任务，供护士、健康管理师或接收机构继续处理。
4. 保存每次分析的输入版本、检索证据、模型与规则版本、人工决定及最终结果。

### 1.2 明确不在首期范围内

- 不自动诊断、开立处方、修改医嘱或签署病历。
- 不在未获医生确认的情况下向患者发送医疗处置建议。
- 不把通用互联网检索结果作为临床知识依据。
- 不在未完成医院审批、授权和脱敏控制时向外部模型传输可识别患者信息。
- 不在 PoC 或单科受控试点向患者开放健康问答、病历解读或病例驱动的对话服务。

## 2. 角色、权限与责任

| 角色 | 可执行操作 | 不可执行操作 |
| --- | --- | --- |
| 经治医生 | 发起分析、审核风险项、确认交接单与随访计划 | 绕过证据或审批直接写入原始 EMR |
| 护士/个案管理师 | 补充交接信息、执行已确认随访任务、记录结果 | 确认临床诊疗结论 |
| 接收方医护人员 | 查看已授权交接单和任务、反馈接收情况 | 查看未授权的完整病历或原始影像 |
| 知识库管理员 | 导入、标注、送审、发布、下架知识文档 | 单独批准临床规则生效 |
| 临床知识审核人 | 审核知识来源、版本、适用范围和失效日期 | 修改患者原始数据 |
| 系统管理员/审计员 | 配置身份、权限、系统参数，审计访问和异常 | 查看超出审计必要范围的临床正文 |

权限必须由后端强制执行，并按岗位、患者关系、任务、用途和有效期进行最小授权。界面隐藏不能替代后端鉴权。

助手、知识库和工具还必须采用资源级交集授权：一次请求至少分别校验助手/工作流、所选知识域与文档版本、每个 Agent 工具、病例/FHIR 资源和下游动作的权限。拥有某个助手的访问权，不自动获得其知识库、工具、会话记录或患者数据的访问权；权限继承、公共分享、临时授权和服务账号均须由后端显式计算，并纳入审计。

**服务对象角色（后续阶段）：** 患者本人（只读查看本人的照护计划与教育材料）和家属/照护者（代理查看并记录执行情况）的角色定义于阶段 3 患者端独立立项时补充。阶段 0-2 不实现患者端，但系统设计须预留患者自管 AccessPolicy 和家属代理接口。字段级和条件级权限控制（参照 FHIR AccessPolicy 的 `readonlyFields`/`hiddenFields`/`criteria`/`writeConstraint` 模式）于阶段 1 详细设计时引入，不在 PoC 中实现。

## 3. 核心业务工作流

```text
出院待办触发/医生手动发起
  -> 获取经授权的结构化病历和出院文书
  -> 数据质量与确定性规则校验
  -> RAG 检索可用指南、院内制度和随访 SOP
  -> 任务规划 Agent
  -> 病历一致性 Agent 与指南合规 Agent 并行分析
  -> 自检 Agent 复核并抑制低证据或重复风险项
  -> 医护人工审核（医生模拟确认/驳回/编辑/升级）
  -> 生成待签署交接单与随访任务草稿
  -> 仅记录模拟发布状态和下游待办视图（不执行真实签署、发送或写回）
```

### 3.1 规则优先级

按确定性从高到低执行：

1. 权限、患者关联、数据完整性、过敏冲突和必填字段等本地确定性规则。
2. 经审核的结构化业务规则和临床路径。
3. RAG 检索与带引用的指南解释。
4. Agent 归纳、草拟和任务编排。

当数据不足、检索无有效证据或模型异常时，系统必须明确展示"无法判断/需人工补充"，不得生成确定性临床结论。

**出院去向感知的严重度调整：** 自检 Agent 在合并风险项时须根据患者 `dischargeTo`（出院去向）动态调整严重度权重——居家（无专业人员监督）时用药/随访缺口严重度上调一级；转护理院/康复机构（有专业人员接管）时可保留或下调一级；转上级医院时保留但附加 `transfer_pending` 标记。权重规则须可配置，默认值由试点医院确认。

### 3.2 集成与数据流边界

系统采用“医院业务系统 -> 统一网关/身份鉴权 -> AI 协同服务 -> 受控存储与审计”的逻辑分层。AI 协同服务可独立部署和版本演进，但不得侵入、替代或直接修改 HIS/EMR/LIS 的核心业务逻辑。

- 业务数据仅通过医院批准的只读 API、消息或中间适配层进入 AI 协同服务；生产阶段的写回仅能由已确认任务通过批准的下游接口完成。
- 知识原文件、知识索引、工作流状态与审计记录逻辑隔离。缓存只能保存经批准的短期数据，不作为病历、审批结果或审计记录的唯一事实来源。
- Agent 间传递使用带 `case_id`、输入版本和最小必要字段的结构化结果；禁止以共享患者全文、未受控会话记忆或直接 RPC 代替数据授权和状态留痕。
- 每个请求应携带可关联的请求标识；跨网关、适配器、检索、模型、人工审核和下游发布的日志均可据此追溯。
- 每个输入快照必须记录字段名、标准化后值、来源资源/文书标识、来源更新时间、采集时间、解析/映射版本和快照时间。PoC 病例的字段映射、来源优先级和冲突样例须在测试数据说明中预先固定；未定义的冲突不得由 Agent 自动选择“正确”来源，必须并列展示并进入人工核实。

### 3.3 路由、工具与人工升级

Agent 编排必须先完成权限校验和数据质量校验，再按“确定性规则/结构化查询 -> RAG 检索 -> 受控工具调用 -> Agent 归纳与草拟”的顺序路由。工具调用实行按 Agent 配置的白名单、固定输入输出模式和超时限制；模型不得自行访问数据库、外部网络或下游发布接口。

工具目录必须由服务端根据当前角色、`case_id`、工作流状态和资源权限生成，不能接受前端或模型声明的任意工具标识。每一次工具调用均须再次校验工具本身和其目标资源的权限，并记录实际操作者、服务账号、代表关系（如有）、工具版本、目标资源与结果；内部规划/推理工具不得作为可对外执行的业务工具暴露。

出现以下任一情况时，系统进入“待人工核实/升级”状态，而不是以模型回答代替处理：证据缺失或冲突、关键字段缺失、高严重度风险、检索或模型失败、工具调用失败、人工主动要求复核。具体置信度阈值、严重度分级和升级接收角色由试点医院确认后配置，不在 PoC 中预设。

确定性规则命中、结构化数据冲突和 Agent 结论冲突不得由自检 Agent 静默消除：系统须分别展示各来源结论、规则版本和冲突原因，保持为待审核项，由经治医生作出最终确认、驳回或编辑。任务规划、病历一致性和指南合规 Agent 任一关键节点失败时，默认不生成可模拟发布的交接或随访任务草稿；自检 Agent 失败时保留未去重的原始风险项并标注“自检未完成”。

### 3.4 PoC 病例与任务状态机

PoC 的病例状态依次为：`draft -> analysing -> review_pending -> confirmed/rejected -> task_draft -> simulated_published -> closed`，并可在任意非终态进入 `failed` 或 `cancelled`。当所引用知识被判过期、撤回或被新版本替代时，引用该版本的 `review_pending` 或 `task_draft` 病例进入 `knowledge_changed` 阻断态（详见 §4.4），须经 `reconcile`（重新检索与分析）回到 `review_pending` 后方可继续。系统负责 `analysing`、`review_pending`、`task_draft` 和失败状态；经治医生负责 `confirmed`、`rejected`、`cancelled`、`reconcile`，并可将单个风险项 `escalate`（标记为"需上级复核/需 MDT 讨论"，携带升级原因与目标角色；已升级项不阻止其余确认项继续生成草稿）；护士/个案管理师可在 `task_draft` 或 `simulated_published` 状态下补充指派给本人的任务执行信息（`supplementTask`）。`escalate` 为可选配置——若试点期间升级场景频率低，可由医院决定是否保留为永久动作。任何状态迁移均需记录操作者、时间、原因、前后状态和关联版本，且不能覆盖已保存的审核记录。

PoC 中的 `simulated_published` 只允许出现在演示工作台和模拟下游待办中，不触发真实通知、患者消息、电子签名、医嘱、病历修改或生产接口写回。阶段 1 及以后如需真实发布，须由医院批准另一套已签署的发布状态和任务闭环规则。

每个随访任务草稿至少包含：任务类型、负责角色/模拟接收方、关联 `case_id`、依据的医生确认项和 SOP 版本、计划完成时间、升级条件、当前状态和执行结果字段；缺少任一字段的草稿不得进入 `simulated_published`。

## 4. RAG 知识库需求

### 4.1 知识来源与治理

- 仅接纳权威临床指南、药品说明书、法律法规、院内审批制度、临床路径和经批准的专家共识。
- 每份文档必须维护：来源 URL/文件、版权或使用依据、适用科室和病种、版本、生效日期、失效日期、审核人、发布日期、责任人。
- 文档进入检索库前须经过“导入 -> 解析质检 -> 临床审核 -> 发布”状态流转；下架后不得参与新任务检索。
- 知识库更新周期一般不长于六个月；到期、被替代或撤销的文档进入复审队列。

### 4.2 摄取与检索

- 支持 PDF、Word、Excel、PPT、图片扫描件和结构化数据的受控导入。
- 上传时必须校验文件类型、声明 MIME 类型、大小上限、完整性摘要和来源；不符合要求、无法解析或存在安全风险的文件不得进入待审核知识库。
- 解析结果必须保留原始文档、页码、章节标题、段落或表格坐标，支持人工校正分块。对于表格、流程图和医学影像标注，分块时必须保留其结构化边界（行列位置/区域坐标）和元素类型标记（`table`/`figure`/`image`），不得将表格内容展平为纯文本后分块。引用此类内容时须展示原始表格/图像的坐标范围。
- 每个分块在索引前须经过后处理管道：关键词自动抽取（≤5 个）、适用科室/病种标签（从预定义标签集中匹配至少一个）、有效期语义提取（若文档正文含明确日期约束须提取为结构化 `effective_period`）。后处理结果写入分块元数据随分块一起索引；后处理失败不影响原始分块入库但标记 `postprocess_incomplete`。PoC 阶段可手工预置标签，正式工程引入 LLM 驱动后处理。
- 支持按病种、科室、文档类型、版本、适用人群、有效期和发布状态过滤。
- 使用向量检索、全文检索和重排序的混合检索，各通道权重须可配置且权重和强制校验为 1.0（如 0.6/0.4 向量/全文），防止配置漂移；可选查询改写与上下文压缩，但二者不得改变原文证据。
- 首期以一套经评测通过的嵌入模型、全文检索和重排序建立基线；多嵌入模型、RRF 融合、双向量集合或知识图谱只能在同一评测集证明增益后引入，不以参考项目中的固定模型、维度、权重或性能数字作为本项目要求。
- 每条面向临床的提示必须展示至少一条可点击的来源引用；无有效引用的内容只能作为“待人工核实”草稿，不得进入高风险建议。

### 4.3 知识资产与检索记录

每个展示给用户或写入工作流的引用必须至少包含：`document_id`、文档版本标识、页码/章节/表格坐标（实现字段 `coordinates`，保留 `location` 为兼容字段）、`chunk_id`、被引用原文片段（`excerpt`）、检索时间（`retrieved_at`）和检索策略版本。引用是不可变的审计证据，不得只保留可变的展示链接；原件、索引或界面变化后，仍须能按记录复现当时使用的证据和位置。

知识库须分别维护文档、文档版本、解析/分块结果和发布状态。每个分块至少关联原文位置、解析版本、适用范围、有效期和知识版本；每次检索须记录查询条件、过滤条件、候选文档、重排序结果和最终被 Agent 使用的证据，以便复现临床提示的来源。

### 4.4 知识入库状态与可恢复处理

知识入库采用两段状态机：入库任务状态机（`queued -> parsing -> review_pending | failed`）负责解析与分块处理；文档版本状态机自 `review_pending` 起，采用"`review_pending -> published -> superseded/archived`"状态流转，并支持 `parse_failed`、`index_failed`、`review_rejected` 等显式失败或拒绝状态，以及 `expired`、`withdrawn` 终态。上传成功只表示原件已受控保存，不表示可被检索或已生效。

- 解析、分块、向量/全文索引与审核应是可观察的后台任务，记录任务标识、开始/结束时间、处理数量、失败原因和重试次数；失败重试必须幂等，不能产生重复分块或重复索引。
- 新版本在解析、索引和审核全部完成前，旧的已发布版本继续作为唯一可检索版本；新版本失败、撤回或过期时不得破坏已有可用知识。
- 分块策略、解析器版本、嵌入模型和索引配置均属于知识版本的一部分。单个文件的重处理只能影响其自身分块与索引，不得通过清空集合、批量重建等方式删除其他已发布知识。
- 入库、重试、发布、下架和删除都须保留责任人、原因和审计记录；删除原件、索引与元数据前须满足医院确认的数据保留与审批规则。

- 新版本发布后发现错误时，可将其标记为 `withdrawn` 并自动激活上一可用已发布版本作为检索版本；分块策略变更后须保留新旧分块的差异元数据，供临床审核人核对变更内容。版本回退动作须记录责任人、原因、回退前后的版本号，并纳入知识生命周期审计事件。

- 当已发布知识被判定过期、撤回或被新版本替代时，所有引用该版本且处于 `review_pending` 或 `task_draft` 的在办病例必须标记为 `knowledge_changed`，清空草稿与任务并阻止进入发布状态。医生须执行 `reconcile`（重置病例、重新检索与重新分析，由 `knowledge_changed` 回到 `review_pending`）完成人工复核后方可继续；具体哪些临床场景必须重新复核，由医院另行确认。已审计的历史输出保留原证据及其当时版本，但须展示失效状态。

## 5. Agent 设计

| Agent | 输入 | 输出 | 人工控制点 |
| --- | --- | --- | --- |
| 任务规划 Agent | 出院小结、患者结构化快照 | 待核验诊断、药物、检验、指南主题 | 不直接产生临床结论 |
| 病历一致性 Agent | 出院小结、医嘱、过敏、检验、诊断 | 缺漏、冲突、剂量或数据不一致项。须覆盖四个子维度并行检查：**用药缺口**（出院医嘱与入院前长期用药的遗漏或未续方）、**检验缺口**（关键检验在出院前未完成或结果未回）、**过敏冲突**（出院用药与已知过敏史交叉比对）、**剂量差异**（出院剂量与入院剂量/指南推荐剂量的显著偏差）。任一维度无数据时标注"数据不足"而非静默跳过 | 高风险项必须显示原始病历字段 |
| 指南合规 Agent | 检索证据、任务计划 | 与指南不一致或缺失的要素 | 必须显示指南版本和原文引用 |
| 自检 Agent | 前两类 Agent 输出 | 合并、去重、降级或驳回的风险项 | 不得删除经确定性规则命中的严重风险，只能标注复核意见 |
| 审核与随访编排 Agent | 医生确认项、患者出院去向、随访 SOP | 交接单和随访任务草稿 | PoC 仅在医生模拟确认后生成模拟发布状态；不得真实签署、发送或写回 |

每个 Agent 输出必须符合固定 JSON/数据契约，至少包含：`case_id`、风险类型、严重度、结论、证据、数据来源、知识库版本、置信说明和需审核动作。涉及工具调用时还必须记录工具名称、参数摘要、返回状态和失败原因。Agent 不得直接写入原始病历。

### 5.1 Agent 输出校验与降级

面向工作流、交接单、任务草稿或图表的数据必须先通过服务端 JSON Schema/字段校验，再交给界面或下游系统使用。校验至少覆盖必填字段、类型、枚举值、数值范围、`case_id` 关联、证据存在性和知识版本有效性；具体临床阈值由经审核的规则配置提供，不能硬编码在提示词或前端。

Agent 输出的每条新增临床内容（风险描述、建议、补充信息）必须标注证据溯源类型：`source_ehr`（来源于原始病历字段，附字段路径）、`source_knowledge`（来源于知识库引用，附知识版本与 chunk_id）、`source_hybrid`（两者组合）、`source_none`（无溯源——此类内容须标记为"待人工核实"，不得自动进入草稿）。溯源标注由各 Agent 在输出 JSON 中逐条携带，自检 Agent 须校验溯源完整性。

模型输出不合法、字段缺失、证据与结论不匹配、引用已失效或工具调用失败时，系统必须保留可审计的失败状态，向用户展示"需人工核实/重新处理"，而不是猜测、截断修复后继续发布。图表或其他结构化展示仅能消费经校验的受限数据模型，禁止把模型生成的任意脚本或配置直接执行于前端。

### 5.2 三类软件助手/机器人

三类能力共用身份鉴权、模型网关、RAG 基础能力、审计、人工升级和可观测性，但不是同一个聊天机器人，也不得共用未经授权的上下文、会话记忆或知识权限。

| 能力 | 服务对象与阶段 | 允许职责 | 明确禁止 |
| --- | --- | --- | --- |
| 医护协同助手 | 已登录的医生、护士、个案管理师；阶段 0 起 | 在已授权的 `case_id` 内发起分析、展示证据和状态、收集人工决定、生成交接单/随访任务草稿 | 自动诊断、绕过医生发布任务、读取无患者关系的病例、直接修改原始 EMR |
| 院内知识问答机器人 | 已登录医护及授权管理人员；阶段 1 候选 | 回答经审核的院内 SOP、系统操作、随访流程和角色权限问题，并提供文档引用 | 用问答替代病例审核、无引用地输出临床结论、向无权限人员披露内部制度或患者数据 |
| 患者流程引导/健康科普机器人 | 患者；阶段 3 独立立项候选 | 基于经批准的公开科普和服务流程提供非诊疗信息、服务引导和人工转接 | 诊断、处方、个体化治疗建议、读取医护端病例上下文、代替紧急医疗处置 |

#### 5.2.1 医护协同助手

- 必须从已登录的工作台进入，并且每次涉及病例的对话均绑定已授权的 `case_id`、角色、用途和有效期；用户可查看当前上下文、清空输入草稿或退出会话。
- 对话仅能调用本需求第 5 节定义的受控 Agent 与工具。任何“生成/发布/写回”意图均先转换为可审查草稿，沿用既有医生确认和发布状态机。
- 回答须区分“病例事实、规则命中、检索证据、Agent 草案和人工决定”；不能把 Agent 的自然语言归纳伪装为原始病历事实或已签署结论。

#### 5.2.2 院内知识问答机器人

- 默认不携带患者、病例或医护历史对话上下文；只有经显式授权且与问答目的相符的最小必要信息才可进入检索条件。
- 知识源与临床 CDSS 知识资产逻辑隔离，至少分为院内流程/SOP、系统帮助和经批准的临床参考资料三类；每类单独维护可见角色、有效期、审核人和版本。
- 回答必须展示来源、版本和适用范围。证据不足、问题超出知识范围、涉及具体病例诊疗、投诉/纠纷、药品不良反应或用户要求人工处理时，停止生成确定性答案并转入医院确认的人工通道。

#### 5.2.3 患者端独立立项门槛

患者端在阶段 3 前不开发、不接入医护端病例工作流。若医院批准立项，必须先完成：服务对象和用途声明、患者身份与知情/隐私方案、公开知识库审核、非诊疗回答策略、紧急情况提示、人工接管通道及响应时限、投诉处理流程、对话记录的最小化保存与删除机制。

面向公众提供生成式人工智能服务时，还必须逐项评估《生成式人工智能服务管理暂行办法》的适用范围；服务适用人群、场合和用途应明确，输入与使用记录应依法保护，投诉处理机制应可用。是否需要安全评估或算法备案，不由本项目预设，而应依据服务的实际属性和主管部门要求判断。

患者端必须采用独立于医护工作台的门户、身份会话和 API 客户端，不允许患者直接登录医护管理界面或取得后台服务账号。若提供患者健康摘要或任务查看，仅能按患者本人授权且经医院确认的 FHIR 资源范围与只读交互访问；患者端不能通过对话、搜索参数或链接枚举其他患者、科室或照护团队的数据。

## 6. 数据、接口与持久化

### 6.1 首期 FHIR 映射目标

| 业务数据 | 首选 FHIR 资源 |
| --- | --- |
| 患者与主索引 | `Patient` |
| 就诊与出院 | `Encounter`、`DocumentReference`、`Composition` |
| 诊断与慢病 | `Condition` |
| 过敏与不良反应 | `AllergyIntolerance` |
| 检验、生命体征、量表 | `Observation`、`DiagnosticReport` |
| 药物与医嘱 | `MedicationRequest`、`MedicationStatement` |
| 随访与照护计划 | `CarePlan`、`Task`、`Appointment` |
| 标准化流程模板 | `PlanDefinition` |
| 授权、数据来源与审计 | `Consent`、`Provenance`、`AuditEvent` |

首期可通过 HIS/EMR/LIS 的既有接口或中间适配层接入；FHIR 是目标数据契约，不要求一次性替换医院现有系统。

**CarePlan 双模式：** 出院交接计划（short-term, intent=plan）和慢病照护计划（long-term, intent=order）作为两条并行 `CarePlan`，通过同一 `subject`（Patient）关联。出院交接计划聚焦出院后 30 天内的随访任务与用药指导；慢病照护计划覆盖长期的指标监测、生活方式干预和定期复查。PlanDefinition 作为标准化模板驱动两模式的实例化——如"心衰出院管理协议"模板实例化为特定患者的出院交接计划，"糖尿病管理指南"模板实例化为慢病照护计划。

FHIR 适配层应能将医院角色、患者关系、科室/组织、照护团队、用途和有效期映射为服务端访问策略。策略至少支持按资源类型、字段、允许的 FHIR 交互（读、创建、更新、操作）和查询条件限制访问；通用的资源读写权限不应自动授予批量操作、账户/归属变更、导出或下游发布等高影响操作。PoC 仅实现模拟只读策略与拒绝用例，不接入真实患者资源。

如后续使用患者关联范围控制访问，需基于医院确认的 FHIR Patient Compartment、组织或照护团队关系定义可见资源集合，而非把某一 `Patient` 的全部关联资源默认暴露给任何具有关联身份的用户。访问策略应以本院数据模型、实际角色和最小必要原则为准，不能照搬参考框架的 compartment 或 account 语义。

### 6.2 工作流状态

每次分析创建独立 `case_id` 和工作流版本，持久化保存输入快照、Agent 节点状态、人工中断点、审核动作、最终发布状态和失败原因。流程可在审核、外部接口失败或模型超时后恢复，但恢复时必须重新校验权限、患者上下文和知识版本。每个需要人工确认的节点前应保存检查点（checkpoint），至少包含输入快照版本、当前知识版本、Agent 中间结果和中断原因；恢复时从最近有效检查点继续，避免重复执行已完成的确定性步骤。PoC 不实现检查点持久化，正式工程参照 langgraph 的 Checkpoint + INTERRUPT/RESUME 模式。

### 6.3 逻辑存储与接口契约

首期至少定义以下逻辑数据边界，不强制具体数据库或中间件选型：

| 逻辑存储 | 承载内容 | 约束 |
| --- | --- | --- |
| 知识原件库 | 已授权的原始知识文件和解析附件 | 保留来源、版本与访问控制；不以向量索引替代原件 |
| 知识索引库 | 分块、向量、全文索引和元数据 | 仅索引已发布且未过期的知识版本 |
| 工作流与审计库 | `case_id`、输入快照索引、节点状态、审核决定、发布事件和检索记录 | 是可恢复与审计的事实来源，具有保留和备份策略 |
| 短期缓存/队列 | 会话上下文、幂等键、受控异步任务和短期结果缓存 | 设置 TTL、访问控制与失败重试；不保存未经批准的原始病历全文 |

当前 PoC 仅对知识子系统实现了本地文件级运行时恢复：知识文档、知识审计和入库任务可写入本地运行时状态并通过“恢复预置样例”回到基线；病例工作流、病例审计和模拟待办仍为进程内存状态，不能视作正式项目的持久化方案。

正式项目仍需将知识原件、知识索引、任务队列、审计记录、身份权限和医院接口适配拆分为独立可治理边界，并与 `poc/` 目录隔离建设，不得直接复用 PoC 运行时文件作为生产事实来源。

所有对 AI 协同服务的调用均应定义版本化 API 契约，最少包含调用者身份/用途、患者或模拟病例上下文、`case_id`、幂等请求标识、输入数据版本、返回状态和错误码。接口适配器负责字段映射与最小必要裁剪，不能把原始生产库连接信息暴露给 Agent。

助手/机器人接口还应声明渠道类型（医护协同、院内问答或患者端）、会话标识、知识域、人工升级状态和关联审计标识。不同渠道的会话、缓存、提示词、知识域和人工队列必须隔离；任何跨渠道复用均需按患者信息和知识权限重新授权。

缓存键必须至少包含医院/租户边界、渠道类型、角色/权限范围、`case_id`（如适用）、知识版本、检索策略版本和输出契约版本。知识发布、下架、权限变化、病例状态变化或人工决定更新时，关联缓存必须主动失效；TTL 只能作为补充，不能使过期知识、越权上下文或已撤回草稿继续返回。缓存、向量库或模型依赖失败时，应回退到经授权的源数据或明确失败状态，不得返回不再适用的缓存答案。

## 7. 安全、隐私与审计

- 医疗健康信息按敏感个人信息处理；实行目的限定、最小必要、单独同意或其他合法处理基础。
- 外部模型、向量库、日志平台和运维人员必须经过数据流向审批；患者可识别字段优先在进入模型前脱敏或令牌化。
- 会话记忆、语义缓存、异步队列和可观测平台同样属于数据流向的一部分；其保存范围、TTL、脱敏方式、访问角色和清理机制须纳入医院审批，不能因其被称为“缓存”而绕过治理。
- 审计日志至少记录：访问者、角色、患者范围、用途、时间、请求、数据版本、检索证据、模型与提示词版本、人工决策和下游发布结果。搜索和读取操作（search/read）同样须生成审计事件——每次查询的记录至少包含完整查询 URL 和参数——"谁查了谁的什么数据"与"谁改了谁的数据"具有同等的可追溯性要求。
- 代表用户执行的服务账号、系统集成账号或 Agent 工具调用还须同时记录服务主体、被代表主体、授权依据、目标 FHIR/业务资源、允许的交互和实际结果；服务账号不得代替临床人员完成签署、发布或其他必须人工确认的动作。
- 对异常大量访问、越权访问、敏感信息导出、模型调用失败和知识库过期建立告警与处置流程。
- 高风险运维访问、数据导出和知识发布的审批方式由医院现行制度确认；系统必须支持单人或双人审批配置，并保留可审查记录。
- 对模型、检索、索引、缓存、消息队列和下游适配器分别提供存活与就绪检查。超时、重试和熔断策略必须区分幂等读取与发布/写回动作：仅允许对安全的幂等操作自动重试，发布类动作必须依赖幂等标识和人工确认，避免重复生成或重复下发任务。

- PoC 不实现紧急访问（break-glass）能力。阶段 1 及以后如需紧急访问，医院必须先定义触发条件、批准人、最小资源范围、有效时长、强制填写的理由、实时告警和事后复核；紧急授权不得成为常规绕过最小授权的路径。
- 审计记录的保留期、权威时间源与时钟同步方式、完整性/防篡改措施，以及审计员读取原始临床正文的限制，均须由医院确认并落实为可验证配置。
- 提示词、模型、临床规则、检索策略或输出契约的每次变更都必须形成版本化变更包，记录责任人、批准人、适用范围、测试案例基线、灰度计划和回滚方式。活动工作流中不得静默替换模型或提示词；变更后发生的问题必须可定位至原版本并可回退。

## 8. 可观测性、评测与验收

### 8.1 运行可观测性

记录单次任务的端到端耗时、各 Agent 节点耗时、模型与提示词版本、工具调用、检索分数、返回文档、人工决策和异常。生产日志不得默认保存原始病历正文或未脱敏提示词。

### 8.2 评测集

由试点科室建设经脱敏的金标准案例集，覆盖：药物遗漏、过敏冲突、检验遗漏、指南不合规、无风险病例、数据缺失、知识过期和模型/接口失败。每个案例要有专家标注的正确结论、证据来源和允许的处理动作。

金标准标签须有明确的临床责任人；至少两名专家意见不一致时，按医院确定的裁决机制记录分歧和最终结论。案例集、标注规则和评分脚本必须版本化并在每轮评测前冻结；评测结果由医院指定的发布责任人审核后方可作为试点准入或版本发布依据。在本院人工流程基线形成前，不预设固定数值阈值。

### 8.3 首期验收条件

1. 任一临床风险项可在界面中追溯至原始病历字段和知识库来源。
2. 医生可确认、驳回或编辑风险项；未确认内容不能发布为患者任务或写回业务系统。
3. 权限、审计、知识版本和工作流状态可按 `case_id` 完整查询。
4. 模型、检索、接口或数据不足时出现明确降级状态，不显示伪成功结果。
5. 试点科室以标注案例集验证缺项发现、引用正确性、误报率、审核耗时和任务闭环率；具体阈值在试点启动前由临床与信息部门共同确定。
6. 用端到端案例验证：相同 `case_id` 可串联输入版本、规则命中、检索证据、Agent/工具调用、人工决定和任务草稿；任何节点失败均保留可解释的失败状态，且不会生成已发布任务。
7. 对知识摄取、检索、Agent 数据契约、权限拒绝、人工中断/恢复和下游发布模拟分别建立自动化测试；PoC 演示不等同于这些测试通过。

8. 覆盖知识入库的重复提交、解析/索引失败、失败重试、版本发布/撤回、旧版本回退、缓存主动失效和审计查询；不得以“索引任务执行成功”替代对可检索版本与引用结果的验证。
9. 使用反例验证 Agent 输出校验：非法 JSON、字段类型错误、范围越界、缺少来源、来源失效、工具超时和模型超时均不得产生可发布任务；针对依赖不可用的情形，分别验证明确降级、健康检查和告警。

### 8.4 助手/机器人专项验收

- 医护协同助手：无病例授权、病例有效期失效或角色权限不足时，不能加载上下文或调用 Agent；有授权时，输出可回溯至同一 `case_id`，且发布动作仍需医生确认。
- 院内知识问答：每个答案显示来源；过期、下架或无权限文档不可被检索；问诊、诊断、投诉、纠纷和不良反应等越界问题能够稳定进入“人工处理/无法回答”路径。
- 患者端：在未独立立项和验收前不提供服务。未来上线前，必须使用专门的边界案例集验证非诊疗策略、紧急提示、人工接管、隐私删除、投诉处理与渠道隔离，不能以医护端 PoC 测试替代。
- 检索降级链：系统须定义完整的检索降级策略——三级回退链路（重排序 → 默认排序 → 纯 BM25/全文检索 → 规则兜底），每级独立错误处理且不跨级传播异常；降级事件须记录日志含触发原因和恢复时间。此项目作为 §4.2 混合检索的验收配套条件。

### 8.5 PoC 运行与交付验证

PoC 环境应可在隔离测试环境中通过可版本化的部署清单重复搭建；上线或演示前至少执行健康检查、核心流程冒烟测试和失败依赖演练。PoC 的交付物应包含：架构与数据流、知识版本清单、数据契约、接口错误码、测试案例及结果、运行日志查询方式和已知限制。Docker、Kubernetes、Nginx、特定模型或向量数据库均不是本需求的强制选型。

截至 2026-07-15，当前仓库已完成一轮可复现的本地交付验证：PoC 单元测试 39/39 通过、正式契约测试 7/7 通过；浏览器实测知识管理员页面可完成“导入待审核 -> 解析与待审核队列可见 -> 恢复预置样例 -> 队列清空并回到 3 份预置知识”的完整演示链，且页面控制台为 0 error / 0 warning；API 冒烟已验证 `POST /api/v1/knowledge/runtime/reset`、恢复后的 `GET /api/v1/knowledge/documents` 和 `GET /healthz`，以及病例 `knowledge_changed` 阻断、`reconcile` 恢复、`close`/`cancel` 闭环与护士 `supplementTask` 等新增端点（12/12 通过）。这些证据说明 PoC 演示链可跑通，但不替代真实医院接口联调、生产部署验收或临床有效性评估。

当前建议将以下材料视为 PoC 交付基线的一部分并持续维护：

- 需求与证据边界文档；
- 数据模型、状态机、接口契约和 E2E 用例；
- `poc/docs/testing/05-poc-validation-results.md` 中的验证结果；
- `output/playwright/` 中与当前演示剧本对应的截图证据；
- 能重复触发健康检查、API 冒烟和浏览器演示的最小操作说明。

### 10.1 后续候选能力，非本期承诺

- **受控汇总分析 Agent：** 仅面向经授权管理者查询脱敏、聚合后的运营与随访指标。若建设，必须在生成查询前完成用途与隐私意图拦截；以 SQL AST/查询策略校验只读操作、字段白名单和禁止 `SELECT *`；注入行列权限；对结果再次脱敏并完整审计。它不属于 PoC 的临床决策链路，也不能查询或导出可识别患者明细。
- **患者端流程引导/健康科普 Agent：** 仅可在独立立项和医院批准后建设；必须与医护端 CDSS 隔离，使用经审核的非诊疗知识，明确转人工和紧急就医引导。不得把患者端对话、长期画像或语音数据默认与本系统病例工作流互通。
- **语音、知识图谱、多模型检索和跨 Agent 记忆：** 均需独立论证临床收益、隐私影响、资源成本、故障降级和评测方案后再排期。
